# [2번 PC 전용] 배민 매크로 역할 안내 — 하위(bottom) 수집 담당

> 이 문서는 **2번(하위) PC의 Codex**에게 주는 안내다.
> **결론부터: 2번 PC는 코드를 새로 작성할 게 없다. `git pull` + `.env` 확인 + DAG pause 상태 확인만 하면 된다.**
> 중앙 PC에서 이미 코드 변경과 신규 DAG 추가를 진행 중이며, 그 결과는 git으로 내려온다.

---

## 1. 전체 구조 (왜 이렇게 도는가)

배민 매크로는 2대 PC가 **같은 코드**(`dags/db/DB_Beamin_Macro_Dags.py`)를 돌린다.
`.env`의 `BAEMIN_MACRO_ROLE` 값 하나로 각 PC가 맡을 절반이 갈린다.

| | 1번 PC (중앙) | 2번 PC (여기) |
|---|---|---|
| `BAEMIN_MACRO_ROLE` | `top` | **`bottom`** |
| 수집 매장 | 매장명 가나다순 **상위 절반** | 매장명 가나다순 **하위 절반** |
| 인박스 export 폴더명 | `manual__top__<run_id>` | **`manual__bottom__<run_id>`** |
| analytics 적재/검증 | **담당함** (Upload DAG 2개) | **안 함** |

수집 결과는 각 PC가 OneDrive 공유 폴더에 떨군다:

```
COLLECT_DB/영업관리부_수집/_baemin_upload_inbox/
    manual__top__<run_id>/      ← 1번 PC가 넣음
    manual__bottom__<run_id>/   ← 2번 PC(여기)가 넣음
```

**2번 PC의 역할은 여기까지다.** 인박스에 폴더를 떨구면 끝이고,
`analytics/baemin_macro/` 적재·ToOrder 교차검증·텔레그램 알림은 전부 중앙 PC가 한다.
(OneDrive analytics 동시 쓰기 충돌을 막기 위한 설계다.)

---

## 2. 중앙 PC에서 지금 바뀌는 것 (2번 PC가 알아야 할 부분)

### 2-1. 수집 대상이 "테스트 매장 목록" → "전체 매장"으로 교정됨
`dags/db/DB_Beamin_Macro_Dags.py`에서 `TARGET_STORES`가 `DELIVERY_MANUAL_TEST_STORES`
(수동 테스트 매장 몇 개)로 잡혀 있었다. 이러면 `load_accounts()`가 **그 테스트 매장만 먼저
필터링한 뒤** 상/하위로 쪼개기 때문에, "전체 매장의 하위 절반"이 아니라 "테스트 매장의 하위
절반"만 수집된다.

```python
# before
TARGET_STORES = DELIVERY_MANUAL_TEST_STORES

# after
TARGET_STORES: list[str] = []  # empty list means all stores
```

> **2번 PC 영향: 큼.** 이 커밋을 pull하기 전까지는 2번 PC도 하위 절반을 제대로 안 돌고 있다.
> 반드시 pull 후 수집 매장 수를 확인할 것 (아래 3-3).

### 2-2. 하위 PC 도착분 전용 Upload DAG 신설 (중앙 PC에서만 동작)
기존 `DB_Beamin_Macro_Upload_Dags`는 KST 07:40에 한 번만 돌면서 인박스의 **모든**
`manual__*` 폴더를 먹고 삭제한다. 2번 PC가 07:40까지 못 끝내면 하위 데이터가 다음날까지
24시간 밀린다.

그래서 중앙 PC에 `DB_Beamin_Macro_Upload_Pc2_Dags`를 새로 만든다:
- KST 08:00~12:30 사이 30분 간격으로 돌면서
- `manual__bottom__*` 폴더**만** 골라 적재·검증·알림
- 인박스에 bottom 폴더가 없으면 `ShortCircuitOperator`로 downstream 전체 skip (알림 안 감)

> **2번 PC 영향: 이 DAG은 중앙 PC 전용이다. 2번 PC에서는 절대 unpause하지 말 것.**
> 2번 PC에서 켜면 같은 인박스 폴더를 두 PC가 동시에 먹으려다 경합/유실이 난다.

### 2-3. 인박스 폴더명 프리픽스가 필터 기준이 됨
중앙 PC의 새 DAG이 `manual__bottom__*` glob으로 폴더를 고른다.
2번 PC의 `BAEMIN_MACRO_ROLE`이 비어 있으면 폴더가 `manual__<run_id>`로 생겨
**새 DAG이 못 잡는다** (다음날 07:40 run이 뒤늦게 처리 — 데이터 유실은 아니지만 하루 지연).
→ `bottom` 설정 유지가 전제 조건이다.

## 3. 2번 PC에서 실제로 할 일

### 3-1. 코드 받기
중앙 PC 작업 브랜치: `fix/gitpush-pathspec` (remote: `doridang001-lab/doridang_airflow`).
중앙 PC가 커밋·푸시한 뒤 아래를 실행한다.

```bash
git fetch origin
git status                      # 로컬 수정 있으면 먼저 정리/stash
git pull origin fix/gitpush-pathspec
```

> 아직 푸시 전이면 대기. 중앙 PC 쪽에서 "푸시 완료" 신호를 받고 진행할 것.

### 3-2. `.env` 역할값 확인 (가장 중요)
```bash
grep BAEMIN_MACRO_ROLE .env
# 기대: BAEMIN_MACRO_ROLE=bottom
```
값이 다르거나 비어 있으면 `bottom`으로 고치고 컨테이너를 재생성한다.
(`.env`는 git 비추적이라 PC마다 직접 설정해야 한다.)

```bash
docker compose up -d
docker compose exec airflow-scheduler printenv BAEMIN_MACRO_ROLE   # 기대: bottom
docker compose exec airflow-worker    printenv BAEMIN_MACRO_ROLE   # 기대: bottom
```

### 3-3. 수집 매장 분할 확인 (2-1 반영 검증)
```bash
docker compose exec airflow-scheduler python -c "
from modules.transform.pipelines.db.DB_Beamin_collect import load_accounts
from dags.db.DB_Beamin_Macro_Dags import _split_accounts_by_range
acc = load_accounts(target_stores=[], exact=False)
low = _split_accounts_by_range(acc, '하위')
print('전체', len(acc), '-> 하위', len(low))
print('첫/끝:', low[0]['store_name'], '/', low[-1]['store_name'])
"
```
기대: `전체 N -> 하위 N//2 이상`, 매장 수가 수십 개 규모.
**전체가 5~10개 수준으로 나오면 2-1 커밋을 아직 못 받은 것이다.**

### 3-4. DAG pause 상태 확인
```bash
docker compose exec airflow-scheduler airflow dags list-import-errors
docker compose exec airflow-scheduler airflow dags list | grep -i beamin
```

2번 PC에서 **켜야 하는 DAG은 딱 하나**다.

| DAG | 2번 PC 상태 | 비고 |
|---|---|---|
| `DB_Beamin_Macro_Dags` | **unpause (켬)** | KST 03:15 수집 → 인박스 export |
| `DB_Beamin_Macro_Upload_Dags` | **pause (끔)** | 중앙 PC 전용 |
| `DB_Beamin_Macro_Upload_Pc2_Dags` (신규) | **pause (끔)** | 중앙 PC 전용 — 이름에 Pc2가 있다고 여기서 켜면 안 됨 |
| `DB_Beamin_Macro_Dags_Retry` | **pause (끔)** | 중앙 PC 전용 (인박스 안 거치고 analytics 직접 씀) |
| `DB_Beamin_Macro_Pc2_Dags` | **pause (끔)** | 레거시. 다른 인박스(`_baemin_pc2_inbox`)를 쓰며 아무도 안 읽음. 켜면 중복 수집 |

> `DB_Beamin_Macro_Upload_Pc2_Dags`의 "Pc2"는 **"하위 PC가 보낸 데이터를 처리한다"**는
> 뜻이지 "2번 PC에서 돌린다"는 뜻이 아니다. 이름 때문에 헷갈리기 쉬우니 주의.

```bash
# 필요 시
docker compose exec airflow-scheduler airflow dags pause DB_Beamin_Macro_Upload_Dags
docker compose exec airflow-scheduler airflow dags pause DB_Beamin_Macro_Upload_Pc2_Dags
docker compose exec airflow-scheduler airflow dags pause DB_Beamin_Macro_Dags_Retry
docker compose exec airflow-scheduler airflow dags pause DB_Beamin_Macro_Pc2_Dags
docker compose exec airflow-scheduler airflow dags unpause DB_Beamin_Macro_Dags
```

### 3-5. 다음 수집 후 export 결과 확인
03:15 run이 끝난 뒤 공유 인박스에 폴더가 제대로 생겼는지 본다.

```bash
ls "<COLLECT_DB>/영업관리부_수집/_baemin_upload_inbox/"
```
기대: `manual__bottom__scheduled__2026-07-24T...` 형태.
- `manual__<run_id>` (프리픽스 없음)로 나오면 → 3-2 역할값 미적용
- 폴더가 없으면 → `export_to_upload_inbox` task 로그 확인

폴더는 중앙 PC가 적재 후 **삭제**한다. 사라졌다면 정상 처리된 것이다.

## 4. 하지 말아야 할 것 (중요)

- **`analytics/baemin_macro/`에 직접 쓰지 말 것.** 2번 PC는 인박스까지만. OneDrive 동시
  쓰기 충돌로 데이터가 깨진다.
- **Upload 계열 DAG을 unpause하지 말 것.** 같은 인박스 폴더를 두 PC가 동시에 `shutil.rmtree`
  하려다 경합한다.
- **`BAEMIN_MACRO_ROLE`을 `top`으로 바꾸지 말 것.** 두 PC가 같은 절반을 중복 수집하고
  인박스 폴더명까지 겹친다.
- **`COLLECT_RANGE` 상수를 코드에서 직접 고치지 말 것.** 범위는 `.env`의 역할값으로만
  제어한다 (`load_accounts()` 우선순위: `conf` > `params` > `BAEMIN_MACRO_ROLE` > 상수).
- **레거시 `DB_Beamin_Macro_Pc2_Dags`를 되살리지 말 것.** 그 인박스(`_baemin_pc2_inbox`)는
  현재 Upload DAG이 읽지 않는다.

## 5. 문제 생기면 중앙 PC에 알려줄 것

- 03:15 수집이 몇 시에 끝났는지 (중앙 PC의 sweep 시간대 08:00~12:30 안에 드는지 판단용)
- `manual__bottom__*` 폴더가 인박스에 생겼는지 / 언제 생겼는지
- `collect_all` task의 실패 계정·매장 수 (`failed` XCom 요약)
- 수집 매장 수가 3-3 기대치와 다른지
