# Flow 가맹점 프로젝트 수집·적재 파이프라인

## Task

플로우(flow.team) 협업툴에 쌓인 가맹점 방문일지·본사 답변을 API로 수집해 PostgreSQL 3테이블로 적재한다. 목적은 "처음 담당하는 직원도 매장 히스토리를 바로 파악"하는 구조의 데이터 기반을 만드는 것이다. 요약·분류·반복이슈 탐지(LLM 레이어)는 이 테이블 위에서 도는 다음 단계이며 이번 범위가 아니다.

Flow API 연결은 이미 되어 있고, `C:\airflow\data\`(git untracked)에 용인동천점 1개 프로젝트의 실제 API 응답 덤프 10건이 남아 있다. 아래 스키마는 전부 그 덤프를 직접 파싱해 확정한 것이다. **덤프를 만든 스크립트는 리포에 없다** — 응답 구조는 확보됐지만 엔드포인트 URL과 인증 헤더는 미확인 상태다.

## Project Conventions

- logging: `logger = logging.getLogger(__name__)` — `print` 절대 금지
- import 경로: `from modules.transform.utility.XXX import ...` (절대경로)
- 파이프라인 파일 위치: `modules/transform/pipelines/strategy/`
- DAG 파일 위치: `dags/strategy/`
- 스케줄 상수: `from modules.transform.utility.schedule import ...` (하드코딩 금지)
- 경로 상수: `from modules.transform.utility.paths import ...` (하드코딩 금지)
- DAG는 orchestration만. 비즈니스 로직은 전부 `modules/transform/pipelines/`로 보낸다
- `dag_id=Path(__file__).stem`, `catchup=False`, `max_active_runs=1` 기본
- 파이프라인 공개 함수는 `**context`를 마지막에 받고, JSON 직렬화 가능한 타입만 리턴한다 (DataFrame을 XCom으로 넘기지 않는다)
- 직전 단계 산출물은 키워드 인자로 명시해서 받는다. XCom pull/push는 DAG wrapper가 담당하고 파이프라인 함수는 XCom을 모른다
- 내부 로직은 `_` prefix private helper로 분리
- DDL 파일을 만들지 않는다 — 이 프로젝트는 `to_sql` 암묵 생성이 관례다

## 실측한 Flow 데이터 구조 (덤프 검증 완료)

```
프로젝트 (projectId)              ← 매장 1개 = 프로젝트 1개 (총 101개)
 └ 게시글 (postId)                ← 방문일지 / 매장정보 / 오픈진행상황 ...
    ├ outContent                  ← 본문 평문
    ├ remarks[]                   ← 댓글 = 본사 답변·후속조치
    ├ tasks[] / subTasks[]        ← 업무·하위업무
    │   └ COLABO_COMMT_SRNO       ← ★ 하위업무 자체의 postId
    └   └ SUB_TASK_CNT > 0        ← ★ 그 아래 또 하위업무 존재 (실측 3단계)
```

### 발견 1 — 하위업무는 별도 엔티티가 아니라 게시글이다

`오픈 진행상황`(postId=`69590268`)의 하위업무 9개는 각각 postId `69590269`~`69590278`을 가진다.
본문을 함께 저장하려면 하위업무 postId로 **상세 API를 재귀 호출**해야 한다.
→ 하위업무를 별도 테이블로 빼지 않고 `flow_post`에 `parent_post_id` / `depth`로 담는다.

### 발견 2 — 본문 섹션 구분자가 텍스트에 이미 박혀 있으나 템플릿이 일정하지 않다

`70835486`의 `outContent` 실측:
```
[공통 정보]===========[본사정책 안내]
[점주 개별 의견 / 건의사항]============[담당자 최종 의견]
```
그러나 `78555117`은 `1.매장현황 2.광고 3.수익 4.담당자 의견 5.점주님 요청사항` 번호 형식이다.
→ **적재 단계에서 파싱하지 않고 원문을 그대로 저장한다.** 섹션 분리는 LLM 레이어의 몫.

### 발견 3 — 댓글이 두 종류다

- `SYSTEM_REMARK_YN='Y'` → `'대기' → '진행' 상태를 변경하였습니다.` (자동 로그)
- `SYSTEM_REMARK_YN='N'` → 유지성: `1~4월까지는 배달플랫폼 전체 수요가 빠져...` (실제 본사 답변)

→ `is_system` 컬럼으로 구분 저장.

### 발견 4 — 필드 네이밍이 두 종류로 섞여 있다

목록/상세 최상위는 camelCase(`postId`, `registerName`, `registeredDateTime`), 중첩된 `remarks`/`subTasks`/`tasks`는 Flow 내부 UPPER_SNAKE(`COLABO_REMARK_SRNO`, `TASK_NM`, `RGSN_DTTM`, `CNTN`).
→ 정규화 함수에서 snake_case로 통일한다.

### 발견 5 — 댓글 본문에 HTML 멘션 앵커가 섞여 있다

`CNTN` 실측 원문:
```
<a style='font-weight:bold;cursor: pointer;color:#4a4598;' onClick="fn_profile('kdk1402@naver.com');" profile-data='...'>김덕기</a>\xa0매장이전시 상권은 ...
```
→ `BeautifulSoup(...).get_text()`로 평문화하고, 멘션 이름은 `mention_names` 컬럼으로 별도 추출. `\xa0`(non-breaking space) 정리 필요.

## Implementation Steps

### Step 0 — API 계약 확정 (선행 필수, 이게 안 되면 나머지는 의미 없음)

리포에 Flow API 클라이언트 코드가 없다. 확보된 것과 없는 것:

| 확보됨 | 미확보 |
|---|---|
| 응답 스키마 전체 (`C:\airflow\data\raw\*.json`) | 엔드포인트 URL |
| 응답 봉투 `{"response":{"success","code","message","data"}}` | 인증 헤더 이름 (API key를 어디에 싣는지) |
| 커서 페이지네이션 (`hasNext`, `lastCursor`) | |
| `FLOW_API_KEY` (`C:\airflow\.env:7`, 현재 코드에서 참조 0건) | |

필요한 API 3종:
1. 프로젝트 목록 → `{"response":{"data":{"projects":[{"projectId","title","projectUrl"}]}}}`
2. 프로젝트별 게시글 목록 (커서) → `{"response":{"data":{"projectId","hasNext","lastCursor","posts":[...]}}}`
3. 게시글 상세 → `remarks[]` / `subTasks[]` / `tasks[]` 가 함께 채워져 옴

**③ 하나로 댓글·하위업무가 같이 오므로 별도 호출이 필요 없다** (덤프에서 확인).

먼저 Flow 개발자 포털에서 엔드포인트/헤더를 확인하고, 프로젝트 목록 API를 단건 호출해 200 + `success:true`가 오는지부터 검증한다. 엔드포인트를 알 수 없으면 여기서 멈추고 사용자에게 보고한다 — 추측으로 구현하지 않는다.

API 상수는 파일 상단에 `SMP_yogiyo_policy_collect.py:28-34` 스타일로 모아둔다.

### Step 4 — DB 적재

**갱신 정책: 덮어쓰기(스냅샷 없음).** 게시글이 수정되면 최신본만 남는다.
`postgre_db_save`의 기본 `append` 모드는 PK 중복을 스킵해서 게시글 수정을 반영하지 못한다. 반드시 `if_exists="replace"`를 쓴다. 규모(101 프로젝트 × 수십 게시글 = 수천 행)에서 안전하다.

```python
postgre_db_save(project_df, "flow_project", pk_col="project_id", if_exists="replace", add_timestamp=False)
postgre_db_save(post_df,    "flow_post",    pk_col="post_id",    if_exists="replace", add_timestamp=False)
postgre_db_save(comment_df, "flow_comment", pk_col="comment_id", if_exists="replace", add_timestamp=False)
```

- `pk_col` 기본값이 `"order_id"`이므로 **반드시 명시**한다
- 컬럼 순서/집합은 모듈 상수 `_PROJECT_COLS` / `_POST_COLS` / `_COMMENT_COLS`로 고정한다

## Verification Loop

구현 완료 후 아래 루프를 **모든 Test Cases PASS까지** 반복한다.

```
LOOP until all PASS:
  1. Test Cases 1~10 순서대로 실행
  2. FAIL 항목 → 원인 분석
  3. 코드 수정
  4. 전체 Test Cases 재실행
종료 조건: 전체 PASS + Constraints 위반 없음
```

단, **Test Case 1(API 계약)이 FAIL이면 루프를 돌지 말고 즉시 중단하고 사용자에게 보고한다.** 엔드포인트를 추측해서 구현하면 안 된다.

## Constraints

- **엔드포인트를 추측하지 않는다.** Step 0에서 확인 실패 시 중단하고 보고
- **`if_exists="replace"` 필수.** 기본 `append`는 게시글 수정을 반영하지 못한다
- **`pk_col` 반드시 명시.** 기본값이 `"order_id"`라 누락 시 KeyError
- **`MAX_DEPTH = 3` 하드 제한.** 재귀 순환 방지, 방문 postId `set` 관리 필수
- **본문 섹션 파싱 금지.** `outContent` 원문 그대로 저장. 템플릿이 게시글마다 다르다
- **이미지 파일 다운로드 금지.** 개수(`image_cnt`)만 저장
- **DDL 파일 생성 금지.** `to_sql` 암묵 생성이 이 프로젝트 관례
- **`print` 금지.** `logger.info` / `logger.warning` 사용 (기존 yogiyo DAG가 print를 쓰지만 따라하지 않는다)
- 개별 게시글 수집 실패는 `logger.warning` 후 `continue` — 전체를 중단시키지 않는다
- 증분 판정에서 첫 중복 발견 시 `break` 금지 (과거 게시글 수정 반영 필요) — `continue`로 전체 스캔
- 폴더 구조·파일명 변경 금지
- 스냅샷/이력 테이블을 만들지 않는다. 수정되면 덮어쓰기가 요구사항이다

## Do Not Ask — Decide Yourself

- 파일이 이미 존재하면: 덮어쓰기
- import가 모호하면: Reference Code의 패턴 따라가기
- 타입 힌트 여부: 기존 파일과 동일하게 (`List[Dict[str, Any]]` 스타일)
- 주석 여부: 최소화 (WHY만, WHAT 설명 금지)
- 변수명·함수명 스타일: snake_case, 기존 파일과 동일하게
- `post_type` 분류 기준이 애매하면: 제목에 `방문일지` 포함 → `방문일지`, `매장 정보` → `매장정보`, `task_nm`이 있으면 → `업무`, 나머지 → `기타`
- `region` 파싱이 애매하면: `project_name`의 첫 `_` 앞부분. `_`가 없으면 빈 문자열
