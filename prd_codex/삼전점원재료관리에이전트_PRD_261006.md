### 2.2 분류 우선순위

1. 푸드가이드 `(부식)` 계정이면 상품 종류와 관계없이 **현장 직원식대**로 확정한다.
2. 본 계정·물류담은 공급처·상품코드·상품명·규격·단위에 연결된 검수된 분류표를 적용한다.
3. 검수되지 않은 품목은 `미분류`로 남기고 금액과 품목을 표시한다.

비용 구분은 `원재료`, `포장재`, `현장 직원식대`, `기타`, `미분류`로 고정한다.

| 비용 구분 | 적용 기준 | 목표 37% 비교 |
|---|---|---|
| 원재료 | 판매용 식재료·음료 | 포함 |
| 포장재 | 판매·배달용 포장재 | 포함 |
| 현장 직원식대 | 부식 계정의 직원 식사 구매 전액 | 제외·별도 보고 |
| 기타 | 안전화·청소용품 등 | 제외·별도 표시 |
| 미분류 | 판단 근거가 부족한 품목 | 확정 계산에 임의 포함 금지·금액 공개 |

원본 사업장명은 보존하고 관리 매장을 송파삼전점으로 연결한다. 현장 직원식대는 이후 전체 손익에 연결할 때도 직영점 운영비로 한 번만 반영한다.

모델의 품목 분류 제안은 확정 분류표를 자동 변경하지 않는다. 본 계정과 부식 계정에 동일 상품이 있어도 계정별 비용 구분을 유지한다.

마트 v3는 기존 `mart/Logistics/Logistics_product/product_master_input.csv`의 정확한 품목 키와 푸드가이드 대분류를 분류 추천 근거로 읽는다. `review_candidates.csv`의 추천은 확정 분류가 아니다. 별도 로컬 사본에서 `approved_category`와 `approved=Y`를 입력한 행만 기존 분류 설정에 병합한다. 충돌·중복 승인·품목 키 변경은 반영을 거부하며 `(부식)` 계정 우선 규칙을 유지한다.

미분류는 순금액 외에 행수와 절대금액을 보존한다. 구매와 환불이 상쇄되어 순금액이 0원이어도 미분류 행이 있으면 분류 미완료다.

### 2.3 금액·중복·기간 처리

- 매출은 할인 후 `total_price`를 부호 그대로 합산한다. 취소·반품 행의 음수·0원을 유지하고 별도로 재차 차감하지 않는다.
- 매출은 해당 매장 전체를 사용하며 브랜드를 임의로 제한하지 않는다.
- 구매는 원천 기재 금액을 사용한다. 세금을 임의로 가감하지 않는다. 물류담 금액의 세금 기준은 운영 검산에 포함한다.
- 직원식대의 환불·반품도 원천에서 표현된 부호를 유지한다.
- 매출의 동일 `_pk`·동일 내용은 한 번만 집계한다. 동일 키의 상충된 내용은 오류로 처리한다.
- 구매는 상품명·금액이 같다는 이유만으로 행을 제거하지 않는다. 공급처가 다른 거래도 이름만으로 합치지 않는다.
- 구매 출처는 원천 종류·파일 판본·행 위치로 추적한다. 파일이 개정되면 해당 파일을 교체 반영하고 이전 판본과 누적 합산하지 않는다.
- 기본 기준일은 한국시간 전일이며 당일·미래 배송은 실적에서 제외한다.
- 계산 범위의 매출과 구매는 같은 기간을 사용한다.
- 지정한 원천 밖의 구매·지원금·급여는 자동 합산하거나 차감하지 않는다. 추가 구매처는 별도 연결 대상으로 등록한다.

금액은 정수 원 단위, 비율과 전망 평균은 `Decimal`로 계산한다. 출력은 `ROUND_HALF_UP`으로 비율 소수점 한 자리·금액 정수 원 단위에 맞추며 임계치 판정은 반올림 전 값으로 수행한다. 그룹별 금액 대사에는 부동소수점 허용 오차를 두지 않는다.

| 지표 | 산식 |
|---|---|
| 매입액 | 원재료 금액 + 포장재 금액 |
| 매입률 | 매입액 ÷ 할인 후 매출액 |
| 목표 차이 | `(매입률 − 0.37) × 100`, `%p` |
| 목표 대비 초과 매입액 | 매입액 − 매출액 × 0.37 |
| 현장 직원식대 | 부식 계정 금액 합계 |
| 구매 증감액 | 최근 7일 매입액 − 직전 7일 매입액 |

기준일을 D라 할 때 최근 7일은 D-6일부터 D일까지, 직전 7일은 D-13일부터 D-7일까지다.

매출이 0 이하이면 매입률을 반환하지 않는다. 비교 기간 매입액이 0 이하이면 증감률을 반환하지 않고 금액 차이와 사유를 표시한다. 음수 순매입은 반품 가능성을 표시하며 낭비·손실로 해석하지 않는다.

정기 마트는 기준일까지 최근 57일을 읽는다. 기간 지정은 `date_from`~`date_to`와 종료일의 월 누적·8주 분석에 필요한 기간을 함께 확보한다. 매출·구매의 물리 파일 경로 외에 운영체제와 무관한 `source_ref`, 파일 해시, 필터 전 0부터 시작하는 행 위치, `evidence_id`를 보존한다. 매출의 `_pk`와 행 내용 판본도 유지한다.

### 2.4 자료 상태와 목표 적용

| 자료 상태 | 판정 기준 |
|---|---|
| 정상 | 스키마·중복·분류·해당 기간 수집 및 마감 근거가 확인됨 |
| 잠정 | 계산 가능한 자료는 있으나 분류 또는 마감 확인이 남음 |
| 누락 | 필요한 원천 또는 기간이 빠졌음 |
| 오래됨 | 필요한 갱신 시점을 넘겼고 최신 확인이 되지 않음 |
| 검증 실패 | 금액·날짜·키 충돌 등으로 유효한 계산을 만들 수 없음 |

파일 수정시각이나 마지막 거래일만으로 기간 전체의 완료를 판단하지 않는다. 무구매일은 해당 기간 수집 완료 근거가 있을 때만 0으로 처리한다.

운영자가 확인한 마감 범위·판본·확인 근거를 로컬에 기록한다. 원천 개정으로 근거가 달라지면 재검증한다. 확인 전에는 잠정값과 제한을 보여주고 확정적인 목표 초과 판정은 보류한다.

마트 v3의 마감 근거는 날짜·원천·계정 범위의 `slice_hash`, 원천 파일 해시, 확인자·확인 시각·근거를 포함한다. 월별 원천 파일의 다른 날짜만 바뀌면 기존 날짜의 마감을 유지하고, 해당 날짜 데이터가 바뀌면 `오래됨`으로 재검증한다. 무거래일은 명시적인 `no_transactions` 확인이 필요하다. 물류담 개별 행의 `마감됨`은 날짜 전체의 수집 완료를 보증하지 않는다.

`quality_daily`는 원천 수집 상태이며 분류 상태와 결합해 지표의 완료 여부를 계산한다. 매입률은 매출·매입 모두 완료되어야 확정하고, 직원식대는 푸드가이드 완료 여부를 별도로 판정한다. 분류 완료·필요 원천 확보·마감 미확인일 때만 `provisional_purchase_rate_pct`를 제공한다. 미분류·누락·오래됨 또는 매출 0 이하이면 비율을 보류한다.

현재 `오래됨`은 마감 이후 판본·범위 변경으로 판정한다. 미준비 안내와 스냅샷 기준일 확인은 대화 서비스에서 수행한다. 금액·날짜·키 충돌 등 검증 실패는 현재 태스크/명령 실패로 처리하고 유효하지 않은 스냅샷을 게시하지 않는다.

목표 37%는 시범 운영월부터 적용한다. 적용 시작일과 금액 기준 확인 여부를 설정에 저장하며, 과거 기간은 현재 목표를 적용한 참고 비교로 표시한다.

## 3. 기능·파일별 구현·운영 인터페이스

### 3.1 보고·이상 탐지·전망

텔레그램은 **의심되는 점 → 수치 근거 → 확인할 사항**을 최대 3개로 안내한다. “왜 의심해?”, “증가 품목 보기”, “현장 직원식대”, “상세 PDF” 버튼을 제공한다. 다음 순서는 상세 PDF와 전체 요약에 적용한다.

1. 기준일과 자료 상태
2. 월 누적 할인 후 매출
3. 원재료·포장재 매입액과 매입률
4. 목표 37% 대비 차이
5. **직영점 현장 직원식대의 전일·월 누적 금액**
6. 최근 구매 변화와 조건부 월말 전망
7. 근거를 확인할 항목 최대 3개

초기 탐지 규칙:

- 최근 7일 구매액이 직전 7일 대비 **30% 이상이면서 10만 원 이상 증가**
- 특정 날짜 구매액이 직전 8주 동일 요일 평균보다 같은 기준으로 증가하되 유효 표본 4개 이상
- 정상 자료의 월 누적 매입률이 37% 초과

직원식대에는 37% 기준을 적용하지 않는다. 직원식대 증감은 별도로 표시한다. 증가 품목의 금액 기여도를 제시하되 선매입·폐기·낭비 등 실제 원인을 근거 없이 확정하지 않는다. 규칙은 버전이 있는 설정값으로 관리한다. 아침 안내와 함께 새 스냅샷에서 발견한 새 이상을 추가 안내하며 같은 규칙·대상·분석 기간의 반복 발송은 막는다.

월말 전망은 기준일 D의 D-55일부터 D일까지 56일을 고정한 뒤 완료 자료의 동일 요일 평균으로 잔여일 매출과 구매를 각각 계산한다. 잔여일이 멀어져도 표본 기간을 이동시키지 않는다. 확인된 무거래일은 0, 누락일과 구매 분류 미완료일은 해당 표본에서 제외한다. 매출·구매 각각 요일별 표본 4개 미만이거나 월 누적 마감이 미완료이면 전망을 보류한다. 특정 날짜의 이상 탐지는 D-7, D-14, …, D-56의 별도 표본을 사용한다.

- 예상 월매출 = 누적 매출 + 잔여일 예상 매출
- 예상 월매입 = 누적 매입 + 잔여일 예상 매입
- 예상 월말 매입률 = 예상 월매입 ÷ 예상 월매출
- 목표 기준 잔여 매입 여력 = 예상 월매출 × 0.37 − 누적 매입

결과에는 ‘최근 패턴 유지 가정’을 표시한다. 재고·향후 행사·확정 발주 계획을 반영한 예측으로 표현하지 않는다. 월말 확정 시 전망 대신 실적을 반환한다. 직원식대 전망과 전체 손익 전망은 후속 범위다.

서비스 상태는 `LOCAL_DB/samjeon_material_agent/`의 `state.sqlite3`, `reports/<report_date>/`, `queue/`, `logs/`에 둔다. 개발 검증은 전용 작업 폴더 .tmp/samjeon-service를 사용하며 운영 상태와 격리한다. 별도의 서비스 계산 사본이 필요할 때만 `snapshots/<snapshot_id>/`를 사용하며 현재 마트 스테이징 경로와 구분한다.

**SQLite의 쓰기 소유자는 Windows 대화 서비스 하나로 제한한다.** Airflow는 결과·작업 파일을 전달하고 SQLite에 직접 쓰지 않는다. 봇 토큰과 자격증명은 Git·문서·설정 예시에 넣지 않는다. 마트 config.json은 기존 필드만 허용한다. 서비스는 별도 service.json을 사용해 마트 설정과 호환성을 유지한다.

현재 마트 설정 기본값은 `version="defaults-v1"`, `target_rate="0.37"`, `target_start_date=null`, `amount_basis_confirmed=false`, `increase_rate="0.30"`, `increase_won=100000`, `minimum_weekday_samples=4`다. 목표 적용일·금액 기준을 추정해서 채우지 않는다. 목표 적용일 이전을 포함하는 기간은 참고 비교로 유지한다.

### 3.4 현재 인터페이스와 실행 명령

현재 공개 진입점은 `plan_build`, `stage_sales`, `stage_purchases`, `stage_aggregate`, `validate_snapshot`, `publish_snapshot`, `query_snapshot`이다. `MaterialQuery`·`MaterialResult`는 후속 서비스의 개념적 계약이며 해당 이름의 타입이 구현됐다고 간주하지 않는다. 현재는 검증된 딕셔너리와 JSON을 반환한다.

- `schema_version=3`; 완료 여부는 JSON boolean, 금액은 정수 원, 표시 비율은 Decimal에서 반올림한 문자열이다.
- 문맥은 `daily`, `month_to_date`, `requested_period`, `seven_day`, `staff_meal_seven_day`, `alerts`, `forecast`, 근거와 설정 판본을 제공한다.
- `target_comparison_status`는 `공식/참고/보류`를 구분한다. `target_exceeded=true`일 때만 공식 목표 초과로 표현한다.
- `issues`는 우선 확인할 최대 3개이며 전체 문제는 `issues.json`, 총수는 `issues_total`에 보존한다.
- 조회는 동일 스냅샷의 파일 해시·가이드·스키마를 검사한다. v1/v2는 v3 조회에서 거부한다. 범위를 벗어나면 필요한 재계산 시작·종료일을 반환한다.

아래는 현재 지원하는 명령이며 저장소 루트에서 실행한다. `<로컬 스냅샷 폴더>`는 `build`가 반환하는 `stage_dir`로 바꾼다.

```powershell
python -X utf8 -m modules.transform.pipelines.db.samjeon_material_agent doctor --date 2026-10-11
python -X utf8 -m modules.transform.pipelines.db.samjeon_material_agent build --date 2026-10-11 --dry-run
python -X utf8 -m modules.transform.pipelines.db.samjeon_material_agent build --date-from 2026-07-01 --date-to 2026-10-11
python -X utf8 -m modules.transform.pipelines.db.samjeon_material_agent query --snapshot '<로컬 스냅샷 폴더>' --intent staff_meal --date-from 2026-10-01 --date-to 2026-10-11
```

`doctor`, `build --dry-run`, `query`는 파일 저장·모델 호출·발송을 하지 않는다. `build`는 로컬 산출물만 생성하고 OneDrive에 게시하지 않는다. `review-import`·`coverage-import`는 검수한 승인 행을 로컬 설정에 반영한다.

```powershell
python -X utf8 -m modules.transform.pipelines.db.samjeon_material_agent review-import --review '<검수한 로컬 분류표>' --version reviewed-20261012
python -X utf8 -m modules.transform.pipelines.db.samjeon_material_agent coverage-import --date 2026-10-11 --review '<검수한 로컬 마감표>'
```

분류표는 `approved_category`, `approved=Y`를 입력한다. 마감표는 실제 수집·마감을 확인한 후 `confirmation_evidence`, `confirmed_by`, `approved=Y`를 입력하고 0행이면 `no_transactions=Y`도 명시한다. 검수 반영 후 다시 `build`해야 새 판본에 반영된다.

조회 종류는 `summary`, `compare`, `anomalies`, `forecast`, `staff_meal`, `evidence`, `status`다. `summary/staff_meal/evidence/status`는 지정 기간을 조회한다. `compare`는 종료일 기준 최근 7일과 직전 7일, `anomalies`는 종료일의 일별·7일·월 누적 규칙, `forecast`는 종료일 기준 전망이다. 근거는 `--evidence-id`, `--product-key`, `--source`, `--offset`, `--limit`로 제한하며 한 번에 최대 500행이다.

서비스 CLI는 별도 samjeon_material_service 패키지에서 doctor, report --snapshot, service --config를 제공한다. report --dry-run, service --dry-run, doctor는 저장·모델 호출·발송을 하지 않는다. 최초 import의 bytecode 저장도 피하려면 python -B -X utf8로 실행한다. 실제 봇·모델 실연결은 운영 전 확인 항목이다.

### 3.5 일정·대화·실패 처리

**현재 마트 DAG:** `DB_SAMJEON_MATERIAL_MART_TIME = "15,45 9-11 * * *"`로 한국시간 09:15~11:45에 30분 간격이다. `resolve_inputs → build_sales/build_purchases → aggregate → validate → publish` 순서로 실행한다. 기준일은 실행 시작 시 한 번 확정한다. conf는 `sale_date` 또는 `date_from/date_to`만 지원하고 혼용·역전·미래 날짜·알 수 없는 키를 거부한다. 게시 태스크는 승인된 Variable이 `true`일 때만 동작한다. 게시 도중 실패하면 기존 최신 포인터를 유지한다. 현재 DAG는 일시중지 상태다.

**대화 서비스:** 아래 기능을 구현하되 자동 발송·실제 운영 연결은 기본 비활성으로 둔다. 마트 일정과 구분한다.

- 보고 시간은 매일 09:30 KST다. 미준비 안내는 한 번 보내고 30분 간격으로 정오까지 재확인한다.
- DAG 일정 상수는 `0,30 9-12 * * *`로 두고 09:00·12:30 실행은 작업 전에 건너뛴다. 정기 작업 슬롯은 09:30, 10:00, 10:30, 11:00, 11:30, 12:00이다.
- `dag_id=Path(__file__).stem`, `catchup=False`, `max_active_runs=1`, 태스크 시간 제한과 `dagrun_timeout`을 명시한다. 처음 등록할 때 일시정지 상태로 둔다.
- 날짜별 보고 키를 사용해 정기 재확인·수동 재실행이 중복 발송을 만들지 않게 한다.
- 과거 날짜의 수동 계산·백필은 자동 발송하지 않는다.
- 정오 이후에도 새로 게시된 v3 자료에서 새 이상을 발견하면 09:30~21:00 KST에 추가 안내한다. 시간 밖에서는 다음 허용 시간에 처리한다. 서비스는 60초마다 포인터를 확인하며 원천 수집을 직접 실행하지 않는다.
- 전용 텔레그램 봇을 사용하며 기존 운영 봇의 수신을 함께 소비하지 않는다.
- 등록된 사용자 ID와 개인 대화 ID를 모두 검사한다. 초기 자동 보고 수신자는 대표의 등록된 개인 대화 한 곳이다.
- `/help`, `/status`, `/cancel`, `/summary`, `/compare`, `/anomalies`, `/forecast`, `/staff_meal`, `/evidence`를 지원한다.
- 일반 질문은 같은 기능으로 변환한다. 후속 조회 범위는 24시간 유지하고 모호한 요청은 되묻는다. 여러 품목이 매칭되면 선택 버튼을 제시한다. 사용자 설명은 기간·품목·발언자·시각에 연결하며 원천 검수 승인으로 사용하지 않는다. PDF는 선택한 기간·품목과 동일 스냅샷으로 생성한다.
- 요청 수신·수신 위치 갱신을 영속화하고 재시작 시 이미 처리한 요청을 다시 실행하지 않는다.
- 취소 요청은 즉시 기록하고 늦게 도착한 모델 결과는 버린다.
- 발송 결과가 불명확하면 `전송 확인 필요`로 보존하고 자동 재송신하지 않는다.

### 3.6 AI 경로·권한·비용 통제

서비스 어댑터는 조회 계약으로만 모델 출력을 허용하며 숫자·원인 문장은 검증된 계산 결과로 작성한다. 현재 구현은 질문당 1회 호출한다. 마트 v3 자체는 모델 호출·발송을 수행하지 않는다. ai_verified는 운영 계정의 권한·무인 실행·추가 사용 통제 검증 후 설정한다.

Codex는 요청당 최대 2회, 호출당 90초로 제한한다. 등록된 질문·결과 계약 외 임의 파일 읽기·셸·SQL 실행을 허용하지 않는다. 전용 실행 설정과 권한 제한을 검증하고 외부 연결·플러그인을 자동 상속하지 않는다.

모델에는 계산 결과와 필요한 제한된 근거를 전달한다. 숫자·단위·기간은 계산 결과에서 최종 문장에 삽입하고 모델이 새 수치 사실을 임의로 확정하지 못하게 검증한다.

모델 실패·시간 초과·구독 한도 도달 시 정형 보고와 명령 기반 조회를 제공한다. 유료 API나 구매 크레딧으로 자동 전환하지 않는다. 정형 계산까지 불가능하면 마지막 정상 결과의 날짜 또는 자료 부족 사유를 표시한다.

## 4. Git·검증·PR·배포·롤백 절차

### 4.1 현재 저장소에서 확인한 제약

2026-10-06 조사 시점의 작업 브랜치는 `feat/쿠팡누락수집-0928`이며 다른 작업의 변경이 다수 존재한다. 원격은 `origin`, 저장소는 `https://github.com/doridang001-lab/doridang_airflow.git`, PR 대상은 `main`이다. 실제 작업 시작 시 현재 상태를 다시 확인한다.

마트 v3는 사용자 요청에 따라 현재 운영 저장소의 대상 파일에 반영하고 검증했다. 해당 작업에서 커밋·푸시·PR·머지는 수행하지 않았다. 후속 기능 개발과 Git 게시 준비는 기존 미커밋 변경을 보존하면서 별도 작업 폴더에서 진행한다.

기존 `C:\airflow\.claude\scripts\gitpush.sh`는 다음 특성이 있다.

- 파일 목록을 생략하면 `git add .`을 실행한다.
- 이미 feature 브랜치이면 그 브랜치를 사용한다.
- 파일 목록을 지정해도 기존 스테이징 영역의 변경까지 커밋할 수 있다.
- 커밋·푸시·PR 생성을 연속 수행한다.

이 특성을 전제로 아래 검증을 통과한 경우에만 사용한다. Git 게시와 운영 배포는 서로 다른 단계다.

### 4.2 문서 개정과 코드 개발의 구분

**이전 v1.2 문서 개정 기록**

- PRD 파일과 업데이트 로그의 이번 항목만 편집한다.
- 현재 브랜치를 바꾸지 않는다.
- 커밋·푸시·PR 생성·머지·배포는 수행하지 않는다.

**서비스 구현·Git 게시 준비**

- 전용 작업 폴더: `C:\airflow_samjeon_agent`
- 전용 브랜치: `feat/samjeon-material-agent-1006`
- 기준: 작업 시작 시 갱신한 `origin/main`
- 기존 `C:\airflow`의 미커밋 변경을 일괄 복사·stash·초기화하지 않는다.
- 같은 작업 폴더·브랜치가 이미 있으면 소유 작업과 변경 범위를 확인한 뒤 재사용한다. 관련 없는 작업이면 덮어쓰지 않는다.

후속 서비스 구현 또는 게시용 작업 폴더를 준비할 때 사용할 명령이다. 이미 구현된 마트 변경은 관련 파일만 검토해 이관하고 새 작업 폴더 생성으로 기존 구현을 유실하지 않는다. 구현 작업에서 전용 worktree를 준비하며 운영 폴더의 브랜치는 전환하지 않는다.

```powershell
git -C C:\airflow fetch origin

git -C C:\airflow worktree add `
  -b feat/samjeon-material-agent-1006 `
  C:\airflow_samjeon_agent `
  origin/main
```

현재 운영 원천의 스키마와 `origin/main` 코드에 차이가 있어도 다른 작업의 변경사항을 일괄 가져오지 않는다. 신규 원천 연결기에서 필요한 계약을 구현하고 테스트한다.

### 4.3 변경·커밋 대상

Git에 포함하는 것은 코드, 테스트, 비밀값 없는 설정 예시, 운영 문서, PRD와 해당 업데이트 기록이다.

다음은 제외한다.

- OneDrive 원본·실데이터·실데이터 스냅샷
- 봇 토큰·인증정보·운영 설정
- 직원식대 및 매출의 실제 보고 결과
- SQLite·로그·임시 파일·백업

공유 파일은 필요한 변경 부분만 가져온다. 특히 현재 `update_log.md` 전체를 복사해 다른 작업의 기록을 함께 커밋하지 않는다.

게시 요청이 있을 때 **삼전점 기능 코드·테스트·운영 문서를 하나의 기능 커밋과 PR로 게시**한다. 문서만 게시하는 요청이면 문서 전용 커밋·PR로 범위를 제한한다.

코드 기능 게시 커밋 메시지는 `feat: 삼전점 원재료·현장 직원식대 에이전트`, 문서만 게시할 때는 `docs: 삼전점 에이전트 PRD 상세화`를 기본으로 사용한다. 사용자가 커밋 메시지를 지정하면 그 내용을 따른다.

### 4.4 게시 전 필수 검증

게시할 대상 파일을 준비한 전용 작업 폴더에서 실행한다. 이번 PRD 개정에서는 코드 테스트를 재실행하지 않고 직전 구현 검증 결과를 기록한다. 현재 마트 검증 명령은 다음과 같다.

```powershell
git status --short
git diff --check
git diff --cached --name-only

python -X utf8 -m pytest `
  tests/test_samjeon_material_mart.py `
  tests/test_samjeon_material_mart_v3.py -q -p no:cacheprovider

python scripts/harness_cli.py validate --target .

git check-ignore --no-index -v config/samjeon_material_agent.example.json
```

후속 서비스 게시 시에는 추가로 원천·분석·서비스·Codex·보고 DAG 테스트를 해당 구현과 함께 실행한다. 설정 예시의 `git check-ignore` 검사는 저장소용 예시를 실제 생성한 뒤 수행한다. 로컬 검수 폴더의 설정 예시는 Git 게시 대상이 아니다.

통과 조건:

- 게시 준비 시작 시 스테이징 영역이 비어 있다.
- 변경 파일이 이 문서의 대상 목록과 일치한다.
- 테스트와 하네스 검증이 통과한다.
- 실제 데이터·비밀값이 포함되지 않는다.
- 다른 작업의 코드와 업데이트 기록이 포함되지 않는다.
- 설정 예시가 최종 제외 규칙에 막히지 않고 추적 가능하다. `git check-ignore` 출력의 규칙 내용까지 확인한다.

기존 실패가 확인되면 신규 변경으로 발생한 실패와 구분해 기록한다. 원인을 확인하지 않은 채 전체 통과로 보고하지 않는다.

### 4.5 커밋·푸시·PR

사용자가 게시를 요청한 경우 전용 작업 폴더에서 `gitpush.sh`를 사용하되, `--` 뒤에 검토한 파일·신규 패키지 경로를 모두 명시한다. 인수 없는 실행과 `git add .`, 강제 푸시는 사용하지 않는다.

게시에는 .claude/scripts/gitpush.sh의 -- 뒤에 검토한 파일 목록을 모두 지정한다. Windows에서 만든 worktree는 Windows Git Bash로 실행해 .git의 Windows 경로가 유지되게 한다. 스테이징은 비어 있어야 하며 feature 브랜치의 upstream이 origin/main으로 남아 있지 않은지 확인한다.

대상은 마트·서비스 패키지, 두 DAG, 두 하네스 문서, registry·일정의 삼전점 변경, import 부작용을 제거한 패키지 초기화, 서비스 설정 예시·최소 의존성, 시작·등록 스크립트, 삼전점 테스트, PRD·업데이트 로그와 추적 제외 규칙이다.

실제 명령에는 변경된 대상만 포함한다. 예시를 그대로 복사해 관련 없는 기존 변경을 게시하지 않는다. 현재 운영 브랜치에서 이 명령을 실행하지 않는다.

푸시 대상은 `origin/feat/samjeon-material-agent-1006`, PR 기준은 `main`이다. `main` 직접 푸시는 금지한다.

PR에는 다음을 기록한다.

- 해결하는 문제와 사용자에게 달라지는 동작
- `(부식)`의 현장 직원식대 처리
- 데이터·금액·목표 기준
- 테스트 명령과 결과
- 비활성 상태인 기능과 운영 전 입력
- 배포·복구 절차 및 알려진 제한

PR 생성 후 다음으로 예상하지 않은 변경이 없는지 확인한다.

```powershell
git diff --name-status origin/main...HEAD
git diff --stat origin/main...HEAD
git log --oneline origin/main..HEAD
```

파일 목록뿐 아니라 전체 변경 내용도 검토한다. 예상하지 않은 변경이 있으면 머지하지 않는다.

원격 푸시는 성공했지만 PR 생성이 실패한 경우 실패한 단계와 푸시된 커밋을 기록한다. 재시도는 기존 원격 브랜치를 사용해 PR 생성부터 수행하고 동일 변경을 다시 커밋하지 않는다.

기존 PR이 있는지 `gh pr list --head feat/samjeon-material-agent-1006 --state open`으로 확인한다. 기존 PR이 있으면 갱신하고 중복 PR을 만들지 않는다. `gitpush.sh`는 기존 PR 조회·무변경 재시도까지 보장하는 스크립트가 아니므로 실패한 단계만 복구한다.

머지는 사용자의 명시적인 요청 후 수행한다. 요청된 PR 번호를 확인해 다음 명령을 사용한다.

```powershell
gh pr merge <확인한-PR번호> --merge --delete-branch
```

`<확인한-PR번호>`는 명령 실행 전 실제 PR 번호로 바꾼다. 활성 worktree 때문에 로컬 브랜치 삭제가 거절되면 머지 결과와 로컬 정리 상태를 구분해 보고하고 강제로 작업 폴더를 지우지 않는다.

**PR 머지는 운영 배포 완료를 뜻하지 않는다.**

### 4.6 운영 배포

**현재 마트의 다음 운영 단계:** 검수 사본의 품목·날짜별 수집 근거를 확인하고 로컬 설정에 반영한다. 목표 적용일·금액 기준 확인값을 등록한 뒤 새 로컬 스냅샷을 재검증한다. 결과와 변경 범위를 제시해 OneDrive 게시 승인을 받은 후에만 게시 Variable·대상 실행을 활성화한다. 정상 게시 후 최신 포인터와 상태를 확인하고 정기 DAG 재개 여부를 결정한다. 검수 완료 전 관측 스냅샷을 게시하는 경우에도 자료 상태를 정상으로 바꾸지 않는다. 기존 v1 스냅샷은 승인 없이 수정·삭제하지 않는다.

아래는 후속 서비스의 Git 기반 운영 배포 절차다. 마트 로컬 검증과 구분한다.

현재 `C:\airflow`는 다른 작업의 변경이 있는 운영 작업 폴더이므로 전체 `git pull`, 브랜치 전환, 강제 초기화로 배포하지 않는다.

1. 승인된 머지 커밋에서 이번 기능의 변경 파일·변경 부분과 해시를 추출한다.
2. 실행 중인 삼전점 서비스와 신규 DAG를 멈춘 상태에서 적용 가능 여부를 검사한다.
3. 신규 파일은 생성하고 공유 파일은 해당 기능 변경 부분만 적용한다.
4. 기존 내용과 충돌하면 자동으로 덮어쓰지 않고 충돌 경로를 보고한다.
5. DAG import·로컬 계산·설정 검증을 수행한다.
6. 전용 봇과 등록된 수신자, 품목 분류, 마감 근거, 구독 실행 조건을 확인한다.
7. 수신자에게 확인된 시험 보고를 보낸 뒤 서비스와 일일 일정을 활성화한다.
8. 배포 커밋, 적용 파일, 설정 버전, 활성화 시각과 결과를 로컬 배포 기록에 남긴다.

작업스케줄러 이름은 `DoridangSamjeonMaterialAgent`로 고정한다. 전용 운영 계정의 로그인 시 시작하고, 실패 시 재시작하며 중복 인스턴스는 시작하지 않는다. 숨김 창으로 실행한다. 로그아웃·PC 종료·절전 중에는 서비스가 중단될 수 있다는 운영 조건을 명시한다.

운영 설정과 자격증명은 Git에서 복사하지 않는다. 봇과 일정은 기본 비활성 상태로 설치하고 운영 전 조건을 통과한 뒤 활성화한다.

### 4.7 복구

- 우선 삼전점 서비스와 해당 DAG만 중지한다.
- 해당 배포가 변경한 파일·변경 부분만 이전 검증 버전으로 되돌린다. 다른 작업의 변경은 되돌리지 않는다.
- 운영 파일을 교체하기 전 복구용 백업이 필요하면 `C:\Local_DB\temp\backups\samjeon_material_agent\<실행ID>\`에만 보관한다.
- 검증 성공 또는 정상 복구 후 임시 백업을 삭제한다. 복구 실패로 남길 경우 경로·사유·정리 조건을 기록한다.
- SQLite 변경은 버전 관리된 추가형 마이그레이션을 우선한다. 호환되지 않는 DB를 조용히 초기화하지 않는다.
- DB 복원 후에는 자동 발송을 끈 상태로 발송 이력을 대조한다. 복원 때문에 과거 보고가 다시 전송되지 않게 한다.
- 원천 OneDrive 파일은 복구 대상이 아니다.
- Git 전체 초기화나 광범위한 파일 되돌리기를 복구 수단으로 사용하지 않는다.
