### 2. TotalSummary 비교 시점 정합

**대상**: `_collect_with_retry_on_mismatch`(`DB_Beamin_04_orders.py:300-409`)

`date_filtered=True`(날짜 혼입 감지)는 사실상 **"날짜 필터가 적용되지 않았다"는 확정 신호**다. 그런데 현재는 이 상태에서 필터 전 TotalSummary와 필터 후 rows를 비교해 반드시 불일치를 만들고, 같은 필터를 재적용하며 전체 페이지 수집을 2회 더 반복한다.

```python
# 현재 (:321-353) — 문제 구간
for attempt in range(max_retry + 1):
    expected = _read_total_summary(driver)          # :323  필터 전 값
    ...
    rows = _collect_all_pages(driver, store_info)
    rows, date_filtered = _filter_rows_to_target_date(rows, target_date, store)   # :346  행만 줄어듦
    if date_filtered:
        logger.warning("날짜 혼입으로 TotalSummary 검증 유지 후 재시도 대상 처리: %s", store)
    ...
    vr = _validate_collected(rows, expected)         # :353  줄어든 rows vs 안 줄어든 expected
```

**변경**:
- `expected`를 루프 선두가 아니라 **필터 정착이 확인된 직후 1회** 읽어 재사용한다.
- `date_filtered`가 True면 TotalSummary 비교를 **건너뛰고** 즉시 필터 재적용 분기로 간다.
- **재적용 후에도 혼입이면 그 매장은 `reason="date_filter"` 실패로 조기 종료**한다. 전체 페이지를 다시 긁는 동작을 반복하지 않는다 — 이것만으로 Step 3의 시간 압박이 크게 줄어든다.
- 혼입이 없을 때만 기존 `_validate_collected` 비교를 수행한다.

⚠️ **저장 생략 가드(`:606-612`)는 그대로 유지한다.** 틀린 데이터를 적재하지 않는다는 원래 의도는 옳다. 혼입 상태의 필터 후 rows를 그냥 저장하면 안 된다 — 페이지네이션 조기 종료 사례(`1페이지: 20행 수집` → `마지막 페이지 도달` 인데 기대 35건)가 있어 그날 전량이라는 보장이 없다.

### 3. 레인 시간 예산 가드

**대상**: `retry_collect`(`dags/db/DB_Beamin_Macro_Dags_Retry.py:79-137`), `retry_collect_from_conf`(`modules/transform/pipelines/db/DB_Beamin_retry.py:691`)

- 랜덤 대기 시간도 예산에서 차감한다.
- 미처리분은 residual로 남으므로 기존 attempt 체인(`MAX_ATTEMPTS = 3`, `Dags_Retry.py:30`)이 자연스럽게 다음 회차에 이어받는다.

```python
def _read_total_summary(driver) -> dict | None:
    """현재 필터 조건의 TotalSummary(건수, 금액). 필터 완전 적용 후 호출해야 정확."""
    return driver.execute_script(
        """
        const spans = document.querySelectorAll('span.TotalSummary-module__SysK');
        let count = null, amount = null;
        for (const span of spans) {
            const b = span.querySelector('b.TotalSummary-module__jikm');
            if (!b) continue;
            const val = parseInt(b.textContent.replace(/,/g, ''));
            const fullText = span.textContent.trim();
            if (fullText.endsWith('건')) count = val;
            else if (fullText.endsWith('원')) amount = val;
        }

        """
    )

def _filter_rows_to_target_date(rows, target_date, store) -> tuple[list[dict], bool]:
    """반환값 2번째가 date_filtered — True면 날짜 필터 미적용 확정 신호."""
    row_dates = order_date(pd.Series([row.get("주문시각", "") for row in rows]))
    valid_dates = sorted({v for v in row_dates.tolist() if v})
    if valid_dates == [target_date]:
        return rows, False
    filtered = [row for row, d in zip(rows, row_dates.tolist(), strict=False) if d == target_date]
    logger.warning("주문 날짜 범위 혼입 감지, target_date 행만 저장: %s / target=%s / dates=%s / rows %d→%d",
                   store, target_date, valid_dates, len(rows), len(filtered))
    return filtered, True
```

### beamin_store_io.py — `order_date` (날짜 검증에 재사용)

```python
def order_date(series: pd.Series) -> pd.Series:
    """배민 주문시각에서 주문일자(YYYY-MM-DD)를 추출한다. 파싱 실패는 빈 문자열."""
    matched = series.fillna("").astype(str).str.extract(
        r"^\s*(\d{4})\.\s*(\d{1,2})\.\s*(\d{1,2})\."
    )
    return (matched[0] + "-" + matched[1].str.zfill(2) + "-" + matched[2].str.zfill(2)).fillna("")
```

## Verification Loop

구현 완료 후 아래 루프를 **모든 Test Cases PASS까지** 반복한다.

```
LOOP until all PASS:
  1. Test Cases 순서대로 실행
  2. FAIL 항목 → 원인 분석
  3. 코드 수정
  4. 전체 Test Cases 재실행
종료 조건: 전체 PASS + Constraints 위반 없음
```

## Constraints

- **저장 생략 가드(`DB_Beamin_04_orders.py:606-612`)를 제거하지 말 것.** 틀린 데이터를 적재하지 않는다는 의도는 옳다. 고칠 대상은 "왜 항상 불일치가 나는가"이지 "불일치를 무시하는 것"이 아니다.
- **혼입 상태의 필터 후 rows를 그냥 저장하지 말 것.** 페이지네이션 조기 종료 사례가 있어 그날 전량이라는 보장이 없다.
- `_MAX_VALIDATION_RETRY = 2`, `_ORDER_COLLECTION_ATTEMPTS = 2` 상수를 늘리지 말 것 — 이번 타임아웃의 직접 원인이다.
- `execution_timeout=timedelta(minutes=180)`은 유지하고, 내부 예산을 그보다 짧게(150분) 두어 스스로 빠져나오게 한다.
- 폴더 구조·파일명 변경 금지. 신규 파일 생성 금지.
- 셀렉터 하드코딩은 기존 패턴 유지 (배민 CSS Module 해시 클래스). 새 셀렉터를 임의로 추가하지 말고 기존 것을 재사용한다.

- 파일이 이미 존재하면: 덮어쓰기
- import가 모호하면: Reference Code의 패턴 따라가기

- deadline 예산 기본값: 150분
- 부분 payload push 방식: 계정 단위 누적 + try/finally
