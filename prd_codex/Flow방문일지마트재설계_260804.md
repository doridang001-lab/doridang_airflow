# Flow 방문일지 마트 재설계 — 로컬 LLM 프롬프트 + Power BI 스타 스키마

## Task

Flow 방문일지(가맹점 SV 방문 기록)를 LLM으로 구조화해 마트·학습용 JSONL을 만드는 파이프라인이
실측상 동작하지 않는다. 10건 중 7건이 규칙 fallback이고, LLM 성공분도 스키마가 어긋나 이슈가 유실되며,
`sv_action`은 100% 공백이고 학습용 JSONL은 `"계육_순살품질\n점주 의견: 순살\n담당자 조치: "` 수준이다.

원인은 두 가지다. (1) 프롬프트가 **출력 JSON 스키마를 전혀 알려주지 않고**, 46개 issue_key 목록 전체와
본문을 통째로 던져 로컬 14B 모델이 감당하지 못한다. (2) LLM 실패 응답과 fallback 결과를 **성공으로 간주해
캐시에 영구 저장**해 재시도가 영원히 막힌다.

원문이 이미 반구조화 표(`주제N / 전달내용 / 가맹점의견`)임을 실측으로 확인했으므로
(주제행 1047개 중 전달내용 100%·가맹점의견 96% 채움), **결정론적 세그먼터로 요약 단위와 근거 span을
먼저 확정하고 로컬 LLM은 짧은 분류·요약만 담당**하도록 재설계한다. 산출물은 Power BI 스타 스키마 5테이블.

## Implementation Steps

### 1. `flow_visit_segmenter.py` (신규) — 결정론적 세그먼테이션

**최우선 제약: 이중집계 방지.** 위 실측대로 204건에서 주제표 내부에 번호목록이 또 잡힌다.
전략을 병렬로 돌리지 말고 **문자 오프셋 배타 점유(claim)** 로 구현한다.

```
claimed: list[(start, end)]
1) 주제표 전략   : 주제N 블록을 claim
2) 헤더블록 전략 : 미점유 구간에만 (담당자 의견/점주님 요청사항/건의사항/특이사항/매장현황)
3) 번호목록 전략 : 여전히 미점유인 구간에만 (^\d+[.)] 및 하위 1) 불릿)
4) 잔여 전략     : 앵커 전무 시 문단 단위 분할
```

세그먼트 스키마:
```python
{
  "seg_id": "<post_id>#<start>-<end>",   # 결정론적, 재실행 시 동일
  "post_id": str, "start": int, "end": int,
  "source_kind": "topic_table" | "header_block" | "numbered" | "residual",
  "topic": str | None,
  "sv_action_raw": str,        # 전달내용 원문
  "owner_voice_raw": str,      # 가맹점의견 원문
  "raw_text": str,             # 원문 span (= evidence, 환각 검출 기준)
  "opinion_source": "점주직접" | "담당자판단",
}
```

`opinion_source`는 **문서 구조로 결정한다. LLM에 묻지 않는다.**
- `가맹점의견`/`점주의견` 칸, `점주님 요청사항` 헤더 → `점주직접`
- `전달내용`, `담당자 의견`, `본사정책 안내` → `담당자판단`

정규식은 공백 변형을 흡수하도록 완화: `가맹점\s*의견|점주\s*의견`, `전달\s*내용`,
`방문\s*일자`, `방문\s*목적`.

댓글 노이즈 판정 함수도 여기 둔다 — `is_noise=True`면 프롬프트에서 제외(테이블에는 보존):
멘션 이름 나열만 / 20자 미만이며 첨부·사진 안내 어휘만 / 본문 공백.

모듈 상수 `SEGMENTER_VERSION = "seg_v1"` 을 둔다 (캐시 키에 사용).

`selftest()` 함수를 노출한다 — Test Case 1이 호출한다.

**코드에 `assert`로 고정할 불변식**
- 어떤 두 세그먼트도 오프셋이 겹치지 않는다
- 모든 세그먼트 텍스트는 `content_clean`의 실제 부분문자열이다

### 2. `flow_visit_prompts.py` (신규) — 로컬 LLM 전용 프롬프트

대상 모델은 Ollama의 `qwen2.5:14b`(주) / `gpt-oss:20b`(폴백)다. 클라우드 대형 모델이 아니다.
아래 원칙은 위 "현재 캐시의 실제 결함"에 1:1 대응한다.

| 관측된 실패 | 설계 대응 |
|---|---|
| JSON이 `"묵` 에서 절단 | 출력 필드 수·길이 최소화 |
| gpt-oss 영어 reasoning 누출 | qwen 계열 우선 고정, gpt-oss는 최후 폴백 |
| 스키마 무시하고 제멋대로 키 | 스키마 명시 + few-shot + **부정 예시** |
| `매출_상권악화` 표기 흔들림 | **후보 8개 객관식**으로 축소 |
| 한 호출에 필드 10개 → 붕괴 | **한 호출 = 한 과업** |

원칙:
1. **한 호출 = 한 과업.** 폐쇄형 분류와 생성형 요약을 절대 한 호출에 섞지 않는다.
2. **폐쇄형 우선.** 선택지가 있는 것은 전부 객관식으로 준다.
3. **추출 후 조립.** 요약을 통째로 생성시키지 않고 원문 문장에 번호를 붙여 제시 →
   모델은 **번호만 고르고** → 문장은 코드가 조립한다.
4. **사전 계산 팩트시트를 입력으로.** 원문 덩어리 대신 라벨 붙은 짧은 불릿
   (아래 Reference Code의 `SMD_07_store_ordesr_alert._build_prompt` 형식).
5. **문장이 아니라 명사구.** `"2문장 이내"` 같은 길이 지시는 로컬 모델이 무시한다.
   **개수 + 글자수 상한**으로 준다.
6. **few-shot 2개 + 부정 예시 1개.** 로컬 모델은 패턴을 복사하므로 "이렇게 하지 마라"가 효과 크다.
7. temperature 0 + `format="json"` (`_chat_options_for_model(is_json=True)`가 이미 설정).

#### P1 — 이슈 분류 (폐쇄형만, 생성 없음)

후보 좁히기: 46개 전체를 던지지 않는다. 세그먼트에 taxonomy alias가 걸리는 **상위 8개 + `기타`** 만
번호 매겨 제시한다. alias 히트 0개면 카테고리 4개 중 선택.

```
[역할] 프랜차이즈 본사 SV 방문일지 1건을 분류한다. 아래 근거에 없는 내용은 판단하지 않는다.

[발췌]
주제: {topic}
본사 안내: {sv_action_raw}
점주 발언: {owner_voice_raw}
[본사 댓글] {responder}: {reply_text}      ← 없으면 "없음"

[issue_key — 반드시 이 중 하나를 그대로 복사]
1) 계육_순살품질   (순살, 이취, 잔뼈, 중량 부족)
2) 소스_용량표기   (소포장지, 1인 소스, 소중대)
... (alias 히트 상위 8개)
9) 기타

[status 판정표 — 댓글을 근거로 고른다]
  해결     : 댓글에 조치 완료가 명시됨
  진행중   : 댓글에 검토·확인·피드백 예정이 명시됨
  안내완료 : 댓글에 불가·어려움·현행 유지가 안내됨
  미해결   : 관련 댓글이 없음
[severity] 높음(고객 안전·법적 위험·매출 직접 타격) / 보통 / 낮음(단순 문의·의견)

[출력] JSON 객체 하나만. 설명·코드블록 금지.
{"issue_key":"", "severity":"보통", "status":"미해결", "is_request":false}
```

few-shot 2개는 **실측 데이터로 고정**한다:
- ① 소스 용량표기 원문 + 심성준 댓글("소중대, 1인 소스 글씨 크기 변경 어려움 안내 부탁드립니다")
  → `{"issue_key":"소스_용량표기","severity":"낮음","status":"안내완료","is_request":true}`
- ② 순살 잔뼈 원문(고객 부상·보험 처리 언급) + 댓글 없음
  → `{"issue_key":"계육_순살품질","severity":"높음","status":"미해결","is_request":true}`

이 둘이 status 판정과 severity 기준을 동시에 고정한다.

#### P2 — 이슈 요약 (문장 번호 선택 + 명사구 1개)

```
[역할] 아래 문장 중 핵심을 고르고, 제목을 붙인다. 문장을 새로 쓰지 않는다.

[점주 발언 문장]
 1) 매출은 비슷한데 순수익이 줄었다고 문의
 2) 금액으로 계산하면 체감상 월 약 100만원정도 줄어든것 같다
[본사 안내 문장]
 1) 데이터가 있으면 확인 요청

[출력]
- owner_pick : 점주 발언에서 가장 핵심인 번호 1~2개. 없으면 []
- sv_pick    : 본사 안내에서 가장 핵심인 번호 1~2개. 없으면 []
- issue_label: 이 건의 제목. **명사구 1개, 12자 이내.** 문장·서술어 금지.
               좋은 예) "순살 잔뼈 혼입"
               나쁜 예) "순살에 잔뼈가 나온다고 합니다"
{"owner_pick":[], "sv_pick":[], "issue_label":""}
```

`owner_summary` / `sv_summary`는 **선택된 원문 문장을 코드가 조립**한다. LLM이 문장을 생성하지 않으므로
환각이 원천 차단된다.

#### P3 — 방문 요약 (명사구 + 4지선다)

```
[입력: 사전 계산 팩트시트]
매장 {store_name} / 방문일 {visit_date} / 목적 {visit_purpose}
이번 방문 이슈: {issue_label} ({status}) × N
본사 댓글: {노이즈 제외 요약}

[출력]
- key_points      : 이번 방문의 핵심. **명사구 3개 이하, 각 20자 이내.**
- owner_sentiment : 긍정 / 중립 / 부정 / 불만 중 하나.
                    불만 = 본사를 향한 명시적 불만 표현이 있을 때만.
{"key_points":[], "owner_sentiment":"중립"}
```
`store_status_summary`는 `key_points`를 코드가 결합해 만든다.

#### P4 — 매장 인수인계 카드 (대시보드 4칸, 전부 명사구)

입력은 원문이 아니라 **P1~P3 결과 팩트시트**다.
```
[매장] {store_name} / 방문 {visit_cnt}건 / 최근 {last_visit_date}
[반복 이슈] {issue_label} {cnt}회 ({first_date}~{last_date})
[미해결 이슈] {issue_label} ({visit_date})
[최근 방문 핵심] {key_points}
[본사 답변] {responder}: {reply_text 요약}

[출력] 전부 명사구 리스트. 문장·서술어 금지.
- owner_status    : 점주 현재 상태. 명사구 3개 이하, 각 15자 이내
- key_concerns    : 점주가 중요하게 보는 이슈. 4개 이하, 각 15자 이내
- handling_points : 응대 시 주의점. 3개 이하, 각 20자 이내. 반복 이슈와 미해결 요청 우선
- manager_memo    : 인수인계 배경. 2개 이하, 각 25자 이내. 확인 안 된 추정은 "~추정"으로 끝낸다

좋은 예) "수익 감소 체감", "전 담당자 이슈 추정"
나쁜 예) "점주님께서 수익이 줄었다고 말씀하셨습니다"      ← 문장 금지
{"owner_status":[], "key_concerns":[], "handling_points":[], "manager_memo":[]}
```

공통: `category`는 LLM에 묻지 않는다 — taxonomy가 `issue_key`로 결정한다.

### 3. `qwen_client.py` 수정 — 최소 침습

### 4. `SMP_flow_visit_mart.py` 수정

**4-1. 실패를 실패로 취급 (가장 중요)**
```python
def _is_llm_failure(r) -> bool:
    return not isinstance(r, dict) or "parse_error" in r or "raw_response" in r
```
- LLM 실패 시 **캐시 저장 금지** → 다음 실행에서 재시도
- **fallback(`_heuristic_extract`) 결과도 캐시 금지.** 현재 `llm_extract_issues:532-535`가
  fallback을 캐시에 저장하는 것이 10건 중 7건이 fallback으로 굳은 직접 원인이다
- fallback 표기는 `llm_model="rule_fallback"`으로 통일

**4-2. 캐시 키 — taxonomy/세그먼터 변경이 반영되게**
현재 키 `{post_id}|{content_hash}|{PROMPT_VERSION}`는 taxonomy를 고쳐도 캐시 히트로 반영되지 않는다.
```
P1/P2: seg|{sha1(raw_text+연결댓글)}|{PROMPT_VERSION}|{SEGMENTER_VERSION}|{TAXONOMY_HASH}
P3:    visit|{post_id}|{content_hash}|{sha1(댓글)}|{PROMPT_VERSION}
P4:    store|{project_id}|{sha1(정렬된 seg_id 조합)}|{PROMPT_VERSION}
```
- `TAXONOMY_HASH` = taxonomy 파일 내용 sha1 앞 8자리
- `PROMPT_VERSION`을 `"flow_visit_v2"`로 올린다 → 기존 오염 캐시 10건이 자동 무효화된다
  (캐시 파일 수동 삭제 불필요)
- P1은 세그먼트 텍스트 해시가 키이므로 반복 문구가 매장·방문 간 캐시 공유된다

**4-3. 캐시 I/O** — 현재 post마다 캐시 전체를 rewrite(`_save_cache`)한다. 세그먼트 단위가 되면
호출 수가 늘어 O(n²)가 되므로 루프 종료 시 1회 저장 + `try/finally`.

**4-4. `_resolve_issue_key()` 2차 방어선** (주 방어선은 P1 후보 좁히기)
정확일치 → `카테고리:` 접두사 제거(`"사입: 묵은지_숙성경도"`) → 공백/언더바 제거 정규화
(`매출_상권악화` → `상권악화` ↔ `상권_악화`) → alias 매칭 → 실패 시 `기타`.

**4-5. 환각 검출 가드**
P2/P4 산출 텍스트의 **숫자·금액·기간·비율**을 추출해 `raw_text`+댓글에 존재하는지 검사한다
(예: "월 약 100만원" → `100`이 근거에 있어야 함). 불일치 시 원문 발췌로 대체하고 `grounding_flag=True`.

**4-6. `visit_date` 주입 (기존 버그)**
`llm_extract_issues`에서 각 이슈 dict에 `visit_date`/`post_id`/`store_name`을 채운다.
`build_store_profile:573`이 `issue.get("visit_date")`를 읽는데 현재 그 키가 없어
`recurring_issues`의 `dates`가 전부 `[]`, `first_date`/`last_date`가 `None`이다.
이것이 대시보드 "이슈 연속 히스토리 타임라인"의 데이터 소스다.

**4-7. 그 외**
- `기타` dedupe 붕괴(`_normalize_llm_result:458`의 `seen[key]`)는 세그먼트마다 1행이 되면서 구조적으로 소멸

### 7. `flow_visit_viz.py` (신규) — Power BI 스타 스키마

단일 와이드 테이블로 만들지 않는다. 패널들의 grain이 다르고(매장/이슈/댓글/날짜),
**댓글이 이슈에 N:1이라 한 테이블에 합치면 이슈 행이 곱해져 카테고리 건수가 부풀려진다.**

| 테이블 | grain | 컬럼 |
|---|---|---|
| `fact_issue` | 이슈 1건 | `seg_id`, `store_key`, `project_id`, `visit_date`, `post_id`, `post_url`, `category`, `issue_key`, `issue_label`, `owner_summary`, `sv_summary`, `owner_voice_raw`, `sv_action_raw`, `raw_text`, `opinion_source`, `is_request`, `severity`, `status`, `issue_seq`, `is_recurring`, `issue_recurrence_cnt`, `issue_first_date`, `issue_last_date`, `visit_purpose`, `store_status_summary`, `owner_sentiment`, `author_name`, `llm_model`, `is_fallback`, `grounding_flag`, `source_kind`, `visit_date_source`, `prompt_version`, `generated_at` |
| `fact_followup` | 댓글 1건 | `comment_id`, `store_key`, `post_id`, `visit_date`, `linked_issue_key`, `responder`, `reply_text`, `written_at`, `resolution_status`, `is_noise` |
| `dim_store` | 매장 1행 | `store_key`, `store_name`, `store_name_sales`, `project_id`, `visit_cnt`, `last_visit_date`, `owner_status`, `key_concerns`, `handling_points`, `manager_memo`, `handover_summary`, `owner_sentiment_last` |
| `dim_issue` | issue_key 1행 | `issue_key`, `issue_label_std`, `category`, `aliases` |
| `dim_date` | 날짜 1행 | `date`, `ym`, `year`, `month`, `quarter`, `week_start`, `is_visit_date` |

관계: `dim_store[store_key] 1→* fact_issue` / `1→* fact_followup`,
`dim_date[date] 1→* fact_issue`, `dim_issue[issue_key] 1→* fact_issue`.

카테고리 건수·타임라인은 `fact_issue`의 **측정값으로 유도**한다. 별도 집계 테이블을 만들지 않는다
(중복 저장하면 갱신 시 원본과 어긋난다).

**`store_key` 정규화** (실측상 필수 — 73개 중 20개 미매칭):
공백 제거 → 말미 괄호 주석 제거(`(26.01)`, `(양수)`, `(구. …)`) → 비매장 프로젝트 제외(`[영업관리부]` 등).
`store_name`(Flow 표기)과 `store_name_sales`(매출 마트 표기)를 함께 실어 조인 검증이 가능하게 한다.

**이중집계·타입 방어 (필수)**
- 이슈 0건 방문일지도 `issue_key=null`로 `fact_issue`에 **1행 유지** (없으면 방문 건수가 틀어짐)
- 후속조치는 `fact_followup`에만 둔다. `fact_issue`에 붙이지 않는다
- 날짜 컬럼은 문자열이 아닌 `datetime64`
- `is_request`/`is_recurring`/`is_fallback`/`grounding_flag`/`is_noise`는 `bool` 고정.
  `None` 금지 — Power BI에서 3-state가 되어 필터가 깨진다
- 리스트형(`key_concerns` 등)은 Power BI가 배열을 못 읽으므로 `" · "` 조인 문자열 + 원본 JSON 컬럼 병기

저장은 기존 `_write_parquet_atomic` 재사용 (아래 Reference Code).
기존 4개 테이블(`flow_visit_log`/`_issue`/`_followup`/`flow_store_profile`)은 **그대로 유지**한다.

def _write_parquet_atomic(df: pd.DataFrame, path: Path) -> None:
    path.parent.mkdir(parents=True, exist_ok=True)

    try:

        os.replace(tmp, path)

## Verification Loop

구현 완료 후 아래 루프를 **모든 Test Cases PASS까지** 반복한다.

```
LOOP until all PASS:
  1. Test Case 1(세그먼터) → 2(gold) → 3(파이프라인) → 4(viz) → 5(JSONL) → 6(DAG) → 7(회귀) 순서로 실행
  2. FAIL 항목 → 원인 분석
  3. 코드 수정
  4. 전체 Test Cases 재실행
종료 조건: 전체 PASS + Constraints 위반 없음
```

Test Case 1이 FAIL인 상태로 2 이후를 진행하지 말 것. 세그먼트가 틀리면 뒤가 전부 틀린다.

## Constraints

- **`print` 금지** — 전부 `logger`
- **경로 하드코딩 금지** — `paths.py` 상수만 사용
- **폴더 구조·파일명 변경 금지**
- `query_qwen_json`의 **반환 규약을 바꾸지 말 것.** 실패 시 `{"raw_response","parse_error"}` 반환은
  다른 파이프라인이 의존한다. 판정은 호출측에서 한다
- `query_qwen_json`의 새 파라미터는 **기본값이 기존 동작**이어야 한다
- DAG가 import하는 파이프라인 함수 이름·시그니처를 유지할 것
  (`extract_visit_logs`, `parse_visit_meta`, `llm_extract_issues`, `build_store_profile`,
  `save_visit_mart`, `export_llm_corpus`)
- 기존 4개 마트 테이블(`flow_visit_log`/`_issue`/`_followup`/`flow_store_profile`)을 삭제하지 말 것.
  시각화 테이블은 **추가** 산출물이다
- **LLM 실패·fallback 결과를 캐시에 저장하지 말 것.** 이것이 현재 결함의 직접 원인이다
- 프롬프트에서 한 호출에 폐쇄형 분류와 생성형 요약을 **섞지 말 것**
- 요약 문장을 LLM이 생성하게 하지 말 것 — 번호 선택 후 코드가 조립한다 (P2)
- `bool` 컬럼에 `None`을 넣지 말 것 (Power BI 필터가 깨진다)
- 대상 매장은 `FLOW_VISIT_PROJECT_IDS` 기본값 2개로 고정. 73개 확대는 이번 범위 밖
- 상단 KPI 카드(월 매출·순수익·객단가 등)는 이 파이프라인 범위 밖.
  `dim_store.store_name_sales`로 조인 가능하게 만드는 것까지만 한다

## Do Not Ask — Decide Yourself

- 파일이 이미 존재하면: 덮어쓰기
- import가 모호하면: Reference Code의 패턴 따라가기
- 타입 힌트 여부: 기존 파일과 동일하게 (`from __future__ import annotations` 사용 중)
- 주석 여부: 최소화 (WHY만, WHAT 설명 금지)
- 변수명·함수명 스타일: snake_case, 내부 헬퍼는 `_` 접두사 (기존 파일과 동일)
- gold set 30건 라벨: 실제 데이터를 읽어 직접 판단해 작성
- 프롬프트 few-shot 문구: 실측 데이터에서 직접 추출해 작성
