# 쿠팡확장 orders 수집 — 역삼점(doriys) 반복 타임아웃 해결

## Task

크롬 확장 `doridang_collector_개발용`의 쿠팡이츠 배치 수집에서 **도리당 역삼점(doriys)** 계정만 매일 orders 타임아웃으로 실패한다. 원인은 runner의 orders 대기시간(`COLLECT_TIMEOUT = 600000`, 10분)이 content script의 매장당 수집 예산(480s + 연장 480s×2 = **최대 1440s / 24분**)보다 구조적으로 짧기 때문이다. 주문서가 많은 역삼점은 10분 안에 못 끝나므로 예외 없이 매번 잘린다.

runner의 고정 타임아웃을 **진행(progress) 기반 타임아웃**으로 바꾸고, COLLECT 메시지 채널을 즉시 반환시켜 bfcache 채널 끊김을 제거한다.

## Implementation Steps

### 1. `content/05_main.js` — COLLECT 핸들러에 top-frame 가드 추가

`manifest.json` 이 `all_frames: true` 인데 이 핸들러에는 프레임 가드가 없어 iframe에서도 `runCollector`가 돈다. 배치 경로에만 가드를 건다.

`if (msg?.type === 'COLLECT') {` 블록 진입 직후, `source` 계산 뒤에 삽입:

```js
    // all_frames:true 이므로 iframe에도 COLLECT가 도달한다. 배치 수집은 top 프레임만 수행.
    if (source === 'batch' && window.top !== window.self) {
      sendResponse({ ack: true, source, skippedFrame: true });
      return true;
    }
```

### 2. `content/05_main.js` — `ackOnly` 즉시 ACK 분기

현재는 `await runCollector(...)` 가 끝난 뒤에야 `sendResponse` 하고 `return true` 하므로, **응답 채널이 최대 24분간 열려 있다.** 그 사이 페이지가 언로드/bfcache 되면 sender(runner)가 `The page keeping the extension port is moved into back/forward cache...` 로 reject된다.

`(async () => { ... })()` 안에서:
- 맨 앞(`runnerManaged` 계산 직후)에 `if (msg.ackOnly) sendResponse({ ack: true, source });` 추가
- 기존의 조기 return 두 곳(`stopped: true`, `blocked: true`)과 마지막 `sendResponse({ success: ..., source, result })` 는 **`if (!msg.ackOnly)` 로 감싼다** (중복 sendResponse 방지)

`ackOnly` 를 붙이지 않는 기존 호출자 — `popup.js:479`, `popup.js:505`, `background.js:20`, `background.js:23`, `runner_baemin.js`, `runner_yogiyo.js`, `runner_naver.js`, `runner_naverads.js` — 는 `result` 를 await 하므로 **동작이 그대로 유지되어야 한다.**

동일 파일의 `COLLECT_PIPELINE_ORDERS`(305행 `sendResponse({ ack: true });` 후 비동기 실행)가 이미 쓰는 패턴이니 그대로 따른다.

### 3. `content/05_main.js` — 진행 하트비트 발신

`runCollector(...)` 호출을 15초 주기 하트비트로 감싼다. `try/finally` 로 반드시 정리.

```js
      let hbTimer = null;
      if (msg.ackOnly) {
        hbTimer = setInterval(() => {
          try {
            chrome.runtime.sendMessage({
              type: 'COLLECT_HEARTBEAT',
              payload: { source, progressToken: (Utils?._logLines?.length ?? 0), ts: Date.now() }
            }).catch(() => {});
          } catch (_) {}
        }, 15000);
      }
      let result;
      try {
        result = await runCollector({ /* 기존 인자 그대로 */ });
      } finally {
        if (hbTimer) clearInterval(hbTimer);
      }
```

`progressToken` 은 단순 카운터가 아니라 **진전 지표**여야 한다. `Utils._logLines` (`content/01_utils.js:235`, debug 라인마다 push)의 길이를 쓴다 — 페이지 수집·예산 연장 등 실제 진전이 있을 때만 증가하므로, "살아는 있지만 멈춘" 상태는 토큰이 고정되어 정상적으로 타임아웃된다.

> 하트비트를 `06_batch.js`(collect 래퍼)가 아니라 `05_main.js` 에 두는 이유: `runner.js:29-32` 의 `CONTENT_FILES` 에 **`06_batch.js` 가 빠져 있어** `injectContent()` 재주입 시 로드되지 않는다. `05_main.js` 는 포함되어 있어 어느 경로로 들어와도 하트비트가 산다.

### 5. `runner.js` — `waitMultistore` 를 진행 기반으로 교체

현재 구조(924~970행): `setTimeout(_to, timeoutMs)` 절대 타이머 + `setInterval(_poll, 500)` (STOP 감시).

- 타임아웃 payload를 오해 없게 채운다:

### 8. `runner.js` — COLLECT 전송 강건화 (3곳 공통)

`runner.js:1201`(orders), `1344`(cmg), `1463`(menu) 세 곳 모두 동일 패턴이다. 공통 헬퍼를 하나 만들고 3곳에서 호출한다.

```js
  // COLLECT를 top 프레임에 보내고 ACK를 확인한다. ACK가 없으면 content 재주입 후 1회 재전송.
  async function sendCollectWithAck(tabId, payload, ctx) {
    const msg = { ...payload, ackOnly: true };
    for (let attempt = 1; attempt <= 2; attempt++) {
      try {
        const res = await Promise.race([
          chrome.tabs.sendMessage(tabId, msg, { frameId: 0 }),
          new Promise((_, rej) => setTimeout(() => rej(new Error('ACK 타임아웃 5000ms')), 5000))
        ]);
        if (res?.ack) return true;
        throw new Error(`ACK 없음: ${JSON.stringify(res || null)}`);
      } catch (e) {
        if (attempt === 1) {
          log(`[${ctx.accountId}] ${ctx.category} COLLECT ACK 실패 (1/2): ${e.message} — content 재주입 후 재전송`, 'err');
          if (!await injectContent(tabId)) { /* 아래 실패 처리로 낙하 */ }
          await sleep(300);
          continue;
        }
        const p = { note: `COLLECT 전송 실패: ${e.message}` };
        logIssue({ category: ctx.category, accountId: ctx.accountId, stores: ctx.stores,
                   step: ctx.step, reason: e.message, url: ctx.url, payload: p,
                   action: 'content 주입/탭 상태 확인' });
        settlePendingAsError(ctx.category, p);
        return false;
      }
    }
    return false;
  }
```

각 호출부는 기존 `chrome.tabs.sendMessage(...).catch(...)` 블록을 이 헬퍼 호출로 교체한다. `waitMultistore(...)` 를 **먼저** 등록하고 그 다음 전송하는 현재 순서(완료 신호 유실 레이스 방지)는 **반드시 유지**한다.

`step` 값은 기존 그대로 — orders: `orders_collect_send`, cmg: `` `cmg_collect_send_${attempt}/${MAX_CMG}` ``, menu: `menu_collect_send`.

### runner.js:924-980 (waitMultistore + settlePendingAsError — 수정 대상)

```js
  function waitMultistore(category, timeoutMs = COLLECT_TIMEOUT, context = {}) {
    return new Promise(resolve => {
      const obj = { category, context, settled: false, payload: {}, resolve, _to: null, _poll: null, _stopDeadline: 0 };
      pending = obj;
      obj._poll = setInterval(() => {
        if (stopRequested && !obj.settled) {
          if (!obj._stopDeadline) obj._stopDeadline = Date.now() + STOP_GRACE_MS;
          if (Date.now() < obj._stopDeadline) return;
          obj.settled = true;
          obj.payload = { category, stopped: true };
          logIssue({ level:'warn', category, accountId: context.accountId, stores: context.stores,
            step: context.step || 'wait_multistore', reason: 'STOP 유예시간 초과',
            url: context.url, payload: obj.payload, action: '현재 category 중단 처리' });
          clearInterval(obj._poll); clearTimeout(obj._to); resolve(obj.payload);
        }
      }, 500);
      obj._to = setTimeout(() => {
        if (!obj.settled) {
          obj.settled = true;
          obj.payload = { category, timeout: true };          // ← storeCount/completedCount 없음 = 오진 원인
          logIssue({ level:'err', category, accountId: context.accountId, stores: context.stores,
            step: context.step || 'wait_multistore', reason: `완료 신호 timeout ${timeoutMs}ms`,
            url: context.url, payload: obj.payload,
            action: 'COLLECT 전송 순서 또는 content 완료 신호 확인 필요' });
          clearInterval(obj._poll); resolve(obj.payload);
        }
      }, timeoutMs);
    });
  }

  function settlePendingAsError(category, payload = {}) {
    if (!pending || pending.settled || (pending.category && pending.category !== category)) return false;
```
