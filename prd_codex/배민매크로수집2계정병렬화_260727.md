# 배민매크로수집2계정병렬화

## Task

배민 매크로 수집이 전부 순차라 벽시계 시간이 너무 길다. `DB_Beamin_Macro_Dags` 는 `collect_batch_1 → 2 → 3` 직렬 체인이고 각 배치 안에서도 브라우저 1개로 계정을 하나씩 처리한다(태스크당 300분 × 3배치). 계정 수집을 **최대 2개까지만** 동시에 돌려 벽시계 시간을 약 절반으로 줄인다. 1번째 레인 시작 후 `random(15,20)`초 뒤 2번째 레인이 시작해 로그인 버스트를 피한다.

구현 층은 **Airflow DAG 태스크 2레인**이다. 파이프라인 내부 ThreadPool 방식은 채택하지 않는다(사유는 Constraints 참고).

## 확인된 환경 사실 (재조사 불필요)

- executor = CeleryExecutor (`docker-compose.yaml:56`)
- `selenium_pool` = **3 슬롯 이미 확보됨** → 풀 변경 불필요

## Implementation Steps

### 1. `dags/db/DB_Beamin_Macro_Dags.py` — 상수 정의

- `_LANES: tuple[tuple[str, ...], ...] = (("collect_batch_1", "collect_batch_2"), ("collect_batch_3", "collect_batch_4"))`
- `_LANE_OFFSET_RANGE: tuple[float, float] = (15.0, 20.0)`
- `COLLECT_LANES: int = 2` — **1로 두면 기존 순차 체인으로 즉시 롤백되는 스위치**

### 2. `_split_accounts_by_range` (`:199`) — account_id 그룹 단위 슬라이싱

`batch:N/M` 분기(현재 `:208-226`)는 정렬된 계정 리스트를 인덱스로 자른다. 동일 `account_id` 가 여러 행(매장)으로 들어오면 두 레인에 걸쳐 **같은 Chrome 프로필 디렉터리(`chrome_profiles/{account_id}`)를 동시 사용**하는 치명적 충돌이 난다.

→ 정렬 후 `account_id` 기준 **순서 유지 그룹**을 만들고 그룹 단위로 슬라이스한 뒤 평탄화한다. 계정이 유일한 현재는 동작이 동일하고, 중복이 생겨도 안전해진다. `상위`/`하위` 분기는 손대지 않는다.

```python
batch_match = re.fullmatch(r"batch:(\d+)/(\d+)", normalized_range)
if batch_match:
    batch_index = int(batch_match.group(1))
    batch_total = int(batch_match.group(2))
    if batch_total <= 0 or batch_index < 1 or batch_index > batch_total:
        logger.warning("알 수 없는 COLLECT_RANGE=%r", collect_range)
        return accounts
    # 같은 account_id가 두 배치(=두 레인)로 쪼개지면 Chrome 프로필이 충돌한다
    groups: dict[str, list[dict]] = {}
    for account in ordered:
        groups.setdefault(str(account.get("account_id") or ""), []).append(account)
    group_keys = list(groups)
    start = len(group_keys) * (batch_index - 1) // batch_total
    end = len(group_keys) * batch_index // batch_total
    selected = [a for key in group_keys[start:end] for a in groups[key]]
    ...  # 기존 logger.info 유지
    return selected
```

### 3. 신규 `init_staging(**context) -> str`

`collect_batch` 의 `reset_staging` 책임을 이 태스크로 이관한다. 두 레인이 동시에 `init_empty_staging` 을 호출해 서로의 산출물을 지우는 사고를 원천 차단한다.

```python
def init_staging(**context) -> str:
    dag_run = context.get("dag_run")
    conf = (getattr(dag_run, "conf", None) or {}) if dag_run else {}
    local_analytics, local_baemin = _main_stage_paths(context)
    # run_id가 경로에 포함되므로 "이미 존재" == 같은 run의 이전 시도
    if conf.get("force_restart") or not local_baemin.exists():
        init_empty_staging(local_baemin)
        return f"staging 초기화: {local_baemin}"
    local_baemin.mkdir(parents=True, exist_ok=True)
    logger.info("배민 staging 누적 유지(태스크 재시도): %s", local_baemin)
    return f"staging 유지: {local_baemin}"
```

### 5. `_build_single_dag_three_batches` (`:1445`) → 레인 배선

- 함수명을 `_build_single_dag_parallel_lanes` 로 변경
- `concurrency=2, max_active_tasks=2` (`max_active_runs=1` 유지)
- 배치 태스크 4개 생성. `lane_offset=True` 는 `collect_batch_3` 에만
- `trigger_rule`: 각 레인 첫 태스크(`collect_batch_1`, `collect_batch_3`) = `ALL_SUCCESS`, 두 번째(`collect_batch_2`, `collect_batch_4`) = `ALL_DONE`
- `execution_timeout` 태스크당 300분 유지, `pool="selenium_pool"` 유지
- 배선:

```python
load_task >> init_staging_task
init_staging_task >> b1 >> b2
init_staging_task >> b3 >> b4
[b2, b4] >> retry_task >> export_task >> upload_task >> notify_task
```

- `COLLECT_LANES == 1` 이면 `b1 >> b2 >> b3 >> b4 >> retry_task` 순차 체인 + `max_active_tasks=1` 로 폴백
- `retry_failed` / `export_to_upload_inbox` / `notify_collection_result` 의 `collect_task_ids=list(_BATCH_TASK_IDS)` 는 그대로 → 4개 태스크 XCom이 자동 병합됨

### 6. `modules/transform/pipelines/db/DB_Beamin_retry.py` — 헬퍼 2개 신설

**`split_retry_conf_by_lane(conf: dict, lanes: int = 2) -> list[dict]`**

`failed_account_ids` 를 정렬해 lanes개 그룹으로 나누고, 각 레인 conf에:
- `failed_account_ids`, `failed_accounts_ids_only` : 해당 그룹만
- `failed_stores` / `failed_orders` / `failed_ads` : `item["account_id"]` 가 그룹에 속하는 항목만
- `target_date`, `stability_profile`, `attempt`, `max_attempts`, `retry_history`, `source_dag_id`, `source_run_id`, `notification_context` : 원본 그대로 복사

**한 계정은 반드시 한 레인에만** 들어가야 한다(Chrome 프로필 충돌 방지). 계정이 1개면 레인 2는 빈 conf가 되고, `retry_collect` 의 기존 `has_retry_target` 분기가 "재시도 대상 없음" 페이로드를 밀어준다.

**`merge_retry_payloads(*payloads: dict | None) -> dict`**

`sanitize_retry_payload` 결과 형태(`target_date`, `retry_result`, `store_info_per_account`, `ad_store_infos`)를 합친다.
- `target_date` : 첫 non-null
- `retry_result` : 개행 조인 (빈 문자열 제외)
- `store_info_per_account` : `account_id` 로 묶고 `store_id` 기준 dedupe
- `ad_store_infos` : `(account_id, store_id)` dedupe
- `residual_failed` : 기존 `merge_failed_payloads` 재사용

### 7. `dags/db/DB_Beamin_Macro_Dags_Retry.py`

- `retry_collect` 에 op_kwarg `lane_index: int = 0`, `lanes: int = 1`, `lane_offset: bool = False` 추가. conf를 `split_retry_conf_by_lane(conf, lanes)[lane_index]` 로 좁힌 뒤 기존 로직 그대로 수행
- `lane_offset=True` 이면 기존 `random.uniform(180, 900)` 대기(현재 `:99`) **앞에** `random.uniform(15, 20)` 추가
- 태스크: `retry_collect_1`(lane_index=0), `retry_collect_2`(lane_index=1, lane_offset=True). 둘 다 `pool="selenium_pool"`, `execution_timeout=timedelta(minutes=180)`
- 신규 `merge_retry_payloads` 태스크 — 두 레인의 `retry_payload`/`retry_result` XCom을 병합해 **동일한 키 이름**(`retry_payload`, `retry_result`)으로 push. `trigger_rule=TriggerRule.ALL_DONE`
- `validate_toorder`(`:121`), `validate_ad_funnel`(`:169`), `notify_and_trigger_next`(`:205-206`)의 `xcom_pull(task_ids="retry_collect", ...)` → `"merge_retry_payloads"` 로 변경
- DAG에 `max_active_tasks=2` 명시
- 배선: `t1 >> [r1, r2] >> merge >> t3 >> t4 >> t5`
- `RETRY_LANES: int = 2` 스위치로 1레인 롤백 가능

```python
def local_stage_paths(subdir: str, run_id: str | None = None) -> tuple[Path, Path]:
    local_analytics = LOCAL_DB / subdir
    if run_id:
        local_analytics = local_analytics / safe_run_id_part(run_id)
    return local_analytics, local_analytics / "baemin_macro"

def progress_path(local_analytics: Path, progress_key: str | None = None) -> Path:
    if not progress_key:
        return local_analytics / PROGRESS_FILENAME
    return local_analytics / f"_collect_progress_{safe_run_id_part(progress_key)}.json"

def init_empty_staging(local_baemin: Path) -> None:
    local_root = LOCAL_DB.resolve()
    if local_baemin.exists():
        if not local_baemin.resolve().is_relative_to(local_root):
            raise RuntimeError(f"staging 삭제 범위 오류: {local_baemin}")
        shutil.rmtree(local_baemin)
    local_baemin.mkdir(parents=True, exist_ok=True)
```

1. [단위 테스트] `python -m pytest tests/test_baemin_batch_split.py tests/test_beamin_retry_conf.py tests/test_baemin_collect_resume.py -q` → 기대: 전체 PASS
2. [DAG import] `airflow dags list-import-errors` → 기대: 배민 DAG 관련 오류 0건
3. [메인 DAG 구조] `airflow tasks list DB_Beamin_Macro_Dags --tree` → 기대: `init_staging` 아래 `collect_batch_1`/`collect_batch_3` 이 형제로 분기, `retry_failed` 의 upstream이 `collect_batch_2`+`collect_batch_4`
4. [Retry DAG 구조] `airflow tasks list DB_Beamin_Macro_Dags_Retry --tree` → 기대: `retry_collect_1`/`retry_collect_2` 형제, 그 아래 `merge_retry_payloads`
5. [동시성 설정] `python -c "from dags.db.DB_Beamin_Macro_Dags import dag; print(dag.max_active_tasks, dag.max_active_runs, sorted(dag.task_ids))"` → 기대: `2 1 [...collect_batch_1..4, init_staging...]`
6. [배치 분할] `python -c "from dags.db.DB_Beamin_Macro_Dags import _split_accounts_by_range as s; a=[{'account_id':f'a{i:02d}','store_name':f'매장 {i:02d}'} for i in range(33)]; r=[[x['account_id'] for x in s(a,f'batch:{i}/4')] for i in range(1,5)]; f=[x for b in r for x in b]; print([len(b) for b in r], len(set(f))==33)"` → 기대: 합계 33, 중복 없음 → `True`
7. [계정 무교차 회귀] 같은 `account_id` 가 매장 2행으로 들어간 리스트로 6번을 반복 → 기대: 해당 account_id가 **한 배치에만** 등장
8. [Retry 분할] `python -c "from modules.transform.pipelines.db.DB_Beamin_retry import split_retry_conf_by_lane as sp; c={'failed_account_ids':['a','b','c'],'failed_accounts_ids_only':['a'],'failed_stores':[{'account_id':'a','store':{'store_id':'s1'}}],'failed_orders':[],'failed_ads':[],'target_date':'2026-07-26'}; L=sp(c,2); print([l['failed_account_ids'] for l in L])"` → 기대: 두 리스트 교집합 없음, 합집합 = `['a','b','c']`
9. [Retry 병합] `merge_retry_payloads` 에 같은 `account_id`/`store_id` 를 가진 페이로드 2개를 넣고 → 기대: `store_info_per_account` dedupe, `retry_result` 개행 조인
10. [스킵 로직 회귀] `airflow dags trigger DB_Beamin_Macro_Dags -c '{"stores":["<매장명>"],"run_all_batches":false,"target_date":"2026-07-26"}'` → 기대: `collect_batch_1` 만 실제 수집, 2/3/4는 `배치 스킵` 반환

**실동작 확인 (수동 트리거 후 초반 10분, 위 1~10 PASS 후 수행)**
- Airflow UI에서 `collect_batch_1` 과 `collect_batch_3` 이 **동시에 running**
- `collect_batch_3` 로그에 `레인 B 시작 오프셋` 이 찍히고 두 태스크 `start_date` 차이 15초 이상
- `ls chrome_profiles` — 서로 다른 account_id 프로필 2개 활성
- `docker stats` — Chrome 2개 동시 구동 시 메모리 여유 확인
- `Local_DB/analytics_stage_main/<run_id>/` 에 `_collect_progress_batch_1_4.json` 과 `_collect_progress_batch_3_4.json` 이 **각각** 생성되고 서로 덮어쓰지 않음
- 완료 후 `notify_collection_result` 메일의 계정/매장 수가 순차 실행 때와 동일

## Verification Loop

구현 완료 후 아래 루프를 **모든 Test Cases PASS까지** 반복한다.

```
LOOP until all PASS:
  1. Test Cases 1~10 순서대로 실행
  2. FAIL 항목 → 원인 분석
  3. 코드 수정
  4. 전체 Test Cases 재실행
종료 조건: 1~10 전체 PASS + Constraints 위반 없음
```

## Constraints

- **동시 수집은 정확히 2계정까지.** 3레인 이상으로 늘리지 말 것 (메모리·봇탐지)
- **파이프라인 내부 ThreadPool 방식으로 바꾸지 말 것.** `DB_Beamin_combined.py` 계정 루프는 건드리지 않는다. 아래 공유 가변상태 때문에 스레드 병렬은 위험하며, Airflow 태스크가 별도 프로세스라 전부 자동 해결된다:
  - `beamin_staging.save_progress` tmp 파일명 충돌 (`beamin_staging.py:152`)
  - `DB_Beamin_combined.py:1042-1050` 누산 리스트/metrics 무락 갱신
  - `croling_beamin._reap_zombie_children` 의 `waitpid(-1)` — 다른 워커의 chromedriver 종료코드 가로챔
  - `DB_Beamin_05_ad_funnel.py:161-183` 전역 서킷브레이커
  - `selenium_uc.configure_chrome_temp_root` 의 프로세스 전역 env / `tempfile.tempdir` 변경
  - `patch_baemin_staging_paths` 의 모듈 전역 setattr
- `beamin_stability.py` 의 `max_parallel_accounts` 는 **미사용 데드 노브**다. 이번 작업에서 활성화하지 말 것
- `selenium_pool` 슬롯(3), `airflow.cfg`, `docker-compose.yaml` 은 **변경 불필요**. 건드리지 말 것
- `_build_legacy_batch_dag` (B2/B3 DAG), 알림 포맷, 검증 태스크(`validate_toorder`/`validate_ad_funnel`), `trigger_next_batch` 는 손대지 말 것
- 안정성 프로필은 `safe_daily` 유지. 프로필 값 변경 금지
- 롤백 경로 필수: `COLLECT_LANES = 1` / `RETRY_LANES = 1` 한 줄 변경으로 순차 체인 복귀 가능해야 함
- `sanitize_retry_payload` 가 `residual_failed` 를 떨어뜨려 `notify_and_trigger_next` 의 `residual_failed` 가 항상 `{}` 인 **기존 버그가 있으나 이번 범위 밖**이다. 이번 변경으로 악화시키지만 말고, 고치려 하지 말 것
- 임시/디버그 스크립트를 저장소 루트에 만들지 말 것. 필요하면 `.tmp/` 사용
- 백업 파일(`*.bak`) 생성 금지

## Do Not Ask — Decide Yourself

- 파일이 이미 존재하면: 덮어쓰기
- import가 모호하면: Reference Code의 패턴 따라가기
- 타입 힌트 여부: 기존 파일과 동일하게
- 주석 여부: 최소화 (WHY만, WHAT 설명 금지)
- 변수명·함수명 스타일: snake_case, 기존 파일과 동일하게
- 레인 분할 방식(연속 절반 vs 라운드로빈): 연속 절반(정렬된 그룹을 앞/뒤로 자름)
- `init_staging` 의 pool: 지정하지 않음 (브라우저를 쓰지 않음)
