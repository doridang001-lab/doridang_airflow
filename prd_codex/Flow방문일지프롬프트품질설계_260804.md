# Flow 방문일지 프롬프트·품질 설계

## 목적
Flow 방문일지 마트는 2개 매장(`2466857=동탄영천점`, `2742104=용인동천점`)의 방문글 10건을 원문 기준으로 이슈화한다. 목표는 단순 LLM 요약이 아니라, 신규 담당자와 다음 에이전트가 같은 원문을 기준으로 계속 품질을 올릴 수 있는 구조를 유지하는 것이다.

## 현재 산출물
- 원천 읽기: `MART_DB/flow` 또는 Flow analytics parquet.
- 방문일지 로그: `FLOW_VISIT_LOG_PARQUET`.
- 이슈 테이블: `FLOW_VISIT_ISSUE_PARQUET`.
- 매장 프로필: `FLOW_STORE_PROFILE_PARQUET`.
- 시각화 단일 테이블: `FLOW_VISIT_VIZ_PARQUET`.
- LLM/RAG용 JSONL: `FLOW_VISIT_CORPUS_JSONL`.

OneDrive 실제 산출물은 운영 데이터이므로 수정 전 사용자 승인이 필요하다. 코드는 저장소에서 먼저 고치고, 로컬 드라이런 품질검사 통과 후 DAG 재실행 승인을 받는다.

## v3 개선 배경
저장된 v2 결과를 확인했을 때 기대 이슈 회수율은 높았지만, `4. 홀관련`처럼 제목만 있는 짧은 세그먼트가 GPT-OSS 후보군에 들어가 `계육_순살품질`로 오분류되는 행이 있었다. 원인은 프롬프트 하나가 아니라 후보 생성 구조였다. 매장 힌트 이슈가 alias 근거 없이도 후보에 들어가면, GPT-OSS가 원문 근거 없는 issue_key를 고를 수 있다.

빈값도 같이 확인했다. `sv_action` 빈값은 대부분 원문에 담당자 조치가 없는 이슈라서 원천 테이블에서는 빈값 유지가 맞다. 다만 시각화용 테이블에서는 공백으로 보이면 결측처럼 보이므로 `담당자 조치 기록 없음`, `후속 댓글 없음` 같은 표시값을 채운다. raw 컬럼은 원문 추적을 위해 그대로 둔다.

최종 v3 precision 보정에서는 taxonomy alias도 좁혔다. `발주닷컴`, `사입`, `부담`, `리뷰 이벤트`, `뼈닭` 같은 단독 표현은 다른 맥락에서도 자주 나오므로 자동 coverage 보충 근거에서 제외했다. 그 결과 실제 저장 결과는 issue/viz 96행이고, 남은 fallback 1건은 taxonomy에 없는 `대파 추가 옵션 미진행` 이슈다.

현재 Flow analytics 원천에는 이 2개 매장 방문글이 빠져 있을 수 있다. 이 경우 `extract_visit_logs()`는 기존 `flow_visit_log`를 읽기 전용 fallback 원문으로 사용한다. 이 fallback은 원천 복구 전까지 재분류/시각화 재생성을 가능하게 하기 위한 운영 가드이며, Flow 원천 수집이 정상화되면 analytics 원천이 우선이다.

## 분류 구조
1. `flow_visit_segmenter.segment_post()`가 방문글을 topic table, header block, numbered segment로 나눈다.
2. `flow_visit_prompts.select_issue_candidates()`가 세그먼트 안에서 실제 alias가 잡힌 issue_key만 후보로 만든다.
3. `_segment_has_issue_signal()`이 제목/목차 수준 세그먼트인지 확인한다. 짧고 alias/요청/조치 신호가 없으면 LLM 호출과 fallback 생성을 하지 않는다.
4. `_rule_class_result()`가 alias 점수로 명확한 이슈를 먼저 분류한다.
5. 애매한 세그먼트만 GPT-OSS JSON 분류를 호출한다.
6. `_supplement_post_issue_coverage()`가 글 전체에서 누락된 핵심 alias를 보충한다.
7. 요약은 LLM 생성문이 아니라 원문 문장 pick 기반 deterministic summary로 만든다.

## GPT-OSS 프롬프트 원칙
- 출력은 JSON 객체 1개만 허용한다.
- issue_key는 후보 목록의 따옴표 안 값을 그대로 복사한다.
- 발췌가 제목/목차 수준이고 구체 불만, 요청, 조치, 수치가 없으면 `기타`를 고른다.
- 매장 힌트는 후보 선별 보조 정보일 뿐이며 원문 근거 없이 issue_key를 고르지 않는다.
- 댓글은 같은 글의 보조 근거이며, 발췌와 직접 연결되는 표현이 없으면 분류 근거로 쓰지 않는다.

## 품질검사 기준
사람이 원문 10건을 읽어 만든 기준은 `modules/transform/pipelines/strategy/flow_visit_quality_cases.jsonl`에 둔다. 각 행은 `human_summary`, `expected_issue_keys`, `must_not_keys`, `prompt_notes`를 가진다.

검사는 `flow_visit_quality.evaluate_visit_quality()`가 수행한다.
- 기대 이슈 회수율.
- 글별 누락 issue_key.
- 금지 오분류 issue_key.
- fallback 수.
- 모델 분포.
- 짧은 근거 오분류 의심 수.
- 표시 필드 빈값 수.

최종 검증값:
- 기준 글 수 10.
- issue/viz 96행.
- 기대 이슈 회수율 100%.
- 누락 0.
- 금지 오분류 0.
- 짧은 근거 오분류 의심 0.
- 시각화 표시 필드 빈값 0.

시각화 시뮬레이션 파일:
- `prd_codex/flow_visit_viz_simulation_260804.md`.
- `.tmp/flow_visit_viz_preview.html`.

다음 에이전트는 코드를 고치기 전에 이 JSONL과 `quality_report_markdown()` 결과를 먼저 봐야 한다. 기대 이슈를 바꿔야 한다면 원문을 다시 읽고 `human_summary`와 `prompt_notes`도 같이 수정한다.

## 운영 절차
1. 저장 산출물을 읽어 현재 row 수, 빈값, 모델 분포, 약한 근거 행을 확인한다.
2. 코드에서 candidate/prompt/taxonomy/segmenter 중 원인 파일만 최소 수정한다.
3. `py_compile`과 `pytest tests/test_flow_visit_mart.py`를 실행한다.
4. OneDrive에 쓰지 않는 로컬 드라이런으로 issue/viz 품질을 확인한다.
5. 사용자 승인 후 Airflow DAG `Sales_FlowVisit_01_Mart_Dags`를 실행한다.
6. DAG 성공 후 OneDrive parquet를 다시 읽어 row 수, 품질검사, 빈값 표시 정책을 확인한다.

## 주의
- `flow_visit_taxonomy.json`은 ignored 파일일 수 있어 `git status`에 안 보일 수 있다.
- 원문에 없는 담당자 조치나 점주 의견을 생성해서 채우지 않는다.
- 시각화 표시값과 원문 raw 값은 구분한다.
- 2개 매장 10개 글 기준으로 맞춘 구조라 전체 매장 확대 시 quality case와 taxonomy alias를 먼저 늘린다.
