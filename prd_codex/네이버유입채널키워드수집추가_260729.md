# 네이버 유입채널·유입키워드 수집 추가

## Task

네이버 스마트플레이스 수집기(크롬/웨일 확장)는 현재 통계 요약 카드 2개 지표(`플레이스 유입`, `예약·주문 신청`)만 수집한다.
여기에 **유입분석 탭(`&menu=place&placeTab=inflow`)의 유입채널·유입키워드 리스트**(각 최대 5개, 이름 + 비율) 수집을 추가한다.
퍼센트는 소수로 변환하고(`"25.75%"` → `0.2575`), 기존 요약 수집 동작은 100% 보존한 채 **날짜당 2회 주소 이동**으로 두 데이터를 모두 받아온다.

**작업 대상은 Python/Airflow가 아니라 크롬 확장(JS)이다.** `C:\airflow` 리포지토리 코드는 변경하지 않는다.

## Project Conventions

- 답변·로그·주석은 **한글**로 쓴다.
- 수정은 **최소 범위**로 한다. 기존 동작 코드는 건드리지 않고 대칭 경로를 추가한다.
- content script는 전역 `Sites` 맵에 자기 자신을 등록하는 구조다 — `Sites['naver'] = { name, match(url), _stopFlag, async collect(opts), ... }`.
- 사이트 디스패치는 `content/05_main.js`의 `runCollector()`가 `site.match(url)`로 수행한다.
- 수집 결과 CSV는 `chrome.runtime.sendMessage({type:'DOWNLOAD_CSV', content, filename})` → `background.js`가 다운로드한다. **서버 POST 없음.**
- runner 페이지(`runner_naver.js`)는 content script가 아니므로 `Utils`를 쓸 수 없다. 자체 `toCSV`/`downloadCsv` 헬퍼를 이미 갖고 있으니 그것을 재사용한다.
- 에러는 **에러코드 + 진단정보(diagnostics)** 형태로 반환한다. 기존 코드: `DATE_MISMATCH`, `METRIC_NOT_FOUND`, `METRIC_AMBIGUOUS`, `METRIC_UNSTABLE`, `LOADING_TIMEOUT`, `COLLECT_ERROR`, `STOPPED`.
- 날짜 이동은 **주소(URL) 변경으로만** 한다. 달력 UI를 클릭하지 않는다.
- 파일 수정 전 `.bak_YYMMDD` 백업을 만든다 (폴더에 `runner.js.bak_20260728` 등 기존 관습 있음). OneDrive 동기화 충돌 전례가 있다.

## Implementation Steps

### 1. `content/07_naver.js` — 유입 수집 로직 추가

기존 `Sites['naver']`의 구조(3회 연속 동일값 안정화 + probe + 에러코드 체계)를 **그대로 복제한 대칭 경로**를 추가한다.
**기존 요약 경로 코드(`_waitForStableReport`, `_probeReport`, `_resolveMetricCard`)는 수정하지 않는다.**

#### 1-1. `collect(opts = {})` 분기

현재 시그니처는 `async collect()` (인자 없음)다. `opts`를 받도록 바꾸고 분기한다:

```js
async collect(opts = {}) {
  this._stopFlag = false;
  const part = opts.naverPart === 'inflow' ? 'inflow' : 'summary';
  const target = (location.href.match(/[?&]startDate=(\d{4}-\d{2}-\d{2})/) || [])[1] || '';

  if (window.top !== window) return;
  if (!target) {
    this._sendComplete({ date: '', part, success: false, errorCode: 'DATE_MISMATCH',
      error: 'URL에서 수집 날짜를 찾지 못했습니다.' });
    return;
  }
  if (part === 'inflow') return this._collectInflow(target);

  // ...이하 기존 요약 로직 그대로. _sendComplete 호출에 part: 'summary' 만 추가...
}
```

기존 `_sendComplete` 호출 3곳 모두 페이로드에 **`part` 필드를 추가**한다.
메시지 타입은 기존 `NAVER_STAT_COMPLETE`를 그대로 재사용한다 (runner 쪽 pending 매칭만 확장).

#### 1-2. `_collectInflow(target)` 신규

`collect()`의 요약 경로와 동일한 형태:

```js
async _collectInflow(target) {
  try {
    this._sendLiveLog(`${target} 유입 리스트의 렌더 완료를 확인합니다.`);
    const result = await this._waitForStableInflow(target, 20000);
    if (!result.success) {
      this._sendLiveLog(`${target} 유입 준비 실패 [${result.errorCode}]: ${result.error}`);
      this._sendComplete({ date: target, part: 'inflow', ...result });
      return;
    }
    this._sendLiveLog(
      `${target} 유입 검증 완료: 채널 ${result.channels.length} / 키워드 ${result.keywords.length} ` +
      `(방식=${result.resolveMode}, 안정화 ${result.stableCount}회)`
    );
    this._sendComplete({
      date: target, part: 'inflow',
      channels: result.channels, keywords: result.keywords,
      resolveMode: result.resolveMode, success: true
    });
  } catch (e) {
    const error = String(e?.message || e);
    this._sendLiveLog(`${target} 유입 수집 예외: ${error}`);
    this._sendComplete({ date: target, part: 'inflow', success: false, errorCode: 'COLLECT_ERROR', error });
  }
}
```

#### 1-3. `_waitForStableInflow(target, timeout = 20000)` 신규

`_waitForStableReport`와 **동일한 패턴**(아래 Reference Code 참조):
- 500ms 간격 폴링, `deadline = Date.now() + timeout`
- `this._stopFlag` 확인 → `STOPPED`
- `probe.signature`가 **3회 연속 동일**해야 성공, `stableCount` 반환
- 상태(stateKey)가 바뀔 때만 `_sendLiveLog`
- 타임아웃 시: 마지막 probe가 success면 `METRIC_UNSTABLE`, 아니면 마지막 `errorCode`

`signature = JSON.stringify({ target, channels, keywords })`

#### 1-4. `_probeInflow(target)` 신규 — 검증 순서

1. `_validateTargetUrl(target)` **재사용** (`startDate === endDate === target && term === 'daily'`) → 실패 시 `DATE_MISMATCH`
2. `_validateInflowTab()` **신규** — `params.menu === 'place' && params.placeTab === 'inflow'` → 실패 시 `TAB_MISMATCH` (신규 코드)
3. `_validateDisplayedTerm()` **신규** — `[class*="ButtonSelector_btn_select"]` 중 `_isVisible`인 요소의 `_normalizeText`가 `'일간'` → 아니면 `TAB_MISMATCH`
4. `_validateDisplayedDate(target)` **신규** — `[class*="StatisticsDateFilter_date"]` 텍스트 `26. 7. 28. 화` 파싱 → `2026-07-28`로 정규화 후 target과 비교 → 불일치 시 `DATE_MISMATCH`
   - 파싱 규칙: `/(\d{2})\.\s*(\d{1,2})\.\s*(\d{1,2})\./` → `20{YY}-{MM 2자리}-{DD 2자리}`
   - **유입 경로에만 적용한다.** 기존 요약 경로에 넣으면 그 뷰의 클래스명이 다를 경우 지금까지 잘 되던 수집이 깨진다(회귀).
5. `_resolveInflowLists()` **신규** (1-5)
6. 각 섹션 루트에 `_hasVisibleLoading()` **재사용** → 로딩 중이면 `LOADING_TIMEOUT`
7. 항목 파싱 (1-6)

`_isVisible`, `_normalizeText`, `_hasVisibleLoading`, `_validateTargetUrl`, `_sendLiveLog`, `_sendComplete`는 **전부 기존 것 재사용**.

#### 1-5. `_resolveInflowLists()` — 두 리스트 구분 (다단 폴백)

유입채널과 유입키워드는 **DOM 구조가 완전히 동일**하다. 섹션 제목으로만 구분 가능하므로 `_resolveMetricCard`의 라벨 앵커링 방식을 따른다.

```
scope = document.querySelector('main') || document.body
lists = [...scope.querySelectorAll('ol[class*="inflow_list"]')].filter(this._isVisible)

각 list 마다:
  section = list.closest('[class*="SectionBox_root"]')
         || list.closest('[class*="SectionBox"]')
         || list.closest('section')
         || 상위 4단계 내 조상
  heading = section 내 첫 번째 보이는 (h1..h6 | [class*="SectionBox_title"] | [class*="title" i]) 의 _normalizeText
  /유입\s*채널/ 매칭 → channel 후보
  /유입\s*키워드/ 매칭 → keyword 후보
```

판정:
- channel 후보와 keyword 후보가 **각각 정확히 1개** → 성공, `resolveMode = 'label'`
- 제목을 하나도 못 찾았는데 **보이는 리스트가 정확히 2개** → DOM 순서 폴백
  (index 0 = channel, index 1 = keyword), `resolveMode = 'order'`, `_sendLiveLog`로 경고 출력
- 그 외(후보 0개 / 2개 이상 / 리스트 개수 ≠ 2) → `METRIC_AMBIGUOUS` 또는 `METRIC_NOT_FOUND`

`diagnostics`에 `listCount`, `channelCandidates`, `keywordCandidates`, `headings`(찾은 제목 텍스트 배열)를 담아 로그로 진단 가능하게 한다.

#### 1-6. 항목 파싱과 퍼센트 변환

각 `li[class*="inflow_list_item"]`에서:

| 필드 | 셀렉터 |
|---|---|
| `rank` | `[class*="Statistics_ranking"]` 텍스트 (없으면 인덱스+1) |
| `name` | `[class*="Statistics_name"]` 텍스트 (`_normalizeText`) |
| `percent` | `[class*="Statistics_percent"]` 중 **`[class*="percent_bar"]`가 아닌** 요소 |

퍼센트 선택 로직 (필수):
```js
const pctEl = [...li.querySelectorAll('[class*="Statistics_percent"]')]
  .find(e => !/percent_bar/.test(e.className) && /^\d+(?:\.\d+)?%$/.test(this._normalizeText(e.textContent)));
if (!pctEl) return METRIC_NOT_FOUND;
const ratio = (parseFloat(this._normalizeText(pctEl.textContent)) / 100).toFixed(4);
```

변환 결과: `60.54%`→`"0.6054"`, `25.75%`→`"0.2575"`, `16.67%`→`"0.1667"`, `1.00%`→`"0.0100"`

**빈 리스트 처리**: 방문이 없는 날은 항목 0개가 정상일 수 있다.
섹션은 찾았지만 항목이 0개이고 로딩 표시가 없으면 → `channels: []`로 **성공 처리**한다.
안정화 루프가 `[]` 시그니처를 3회 연속 확인해야 하므로 "아직 안 그려진 상태"와 자연히 구분된다.

### 3. `runner_naver.js` — 날짜당 2단계 수집

#### 3-1. URL 빌더 추가

`urlFor(date)`는 그대로 두고 아래를 추가:
```js
const inflowUrlFor = date => `${urlFor(date)}&menu=place&placeTab=inflow`;
```

#### 3-2. pending 티켓에 `part` 추가

- `waitStat(tabId, date, part, timeoutMs)` — 티켓에 `part` 저장
- `onMessage`의 늦은 응답 가드를 확장:
  ```js
  if ((msg.payload?.part || 'summary') !== pending.part) {
    log(`파트 불일치 응답 무시: 요청=${pending.part}, 응답=${msg.payload?.part || '-'}`, 'err');
    return;
  }
  ```
  기존 `msg.payload?.date !== pending.date` 가드는 유지한다. 요약 응답이 유입 대기 슬롯에 들어가는 교차 오염을 막는다.

#### 3-3. `collectDate` → `collectPart(tabId, date, part, index)`

기존 2회 재시도 구조(실패 시 같은 주소 1회 새로고침 → content 재주입)를 **그대로 유지**하고,
`sendToTopFrame` 메시지에만 `naverPart`를 싣는다:

```js
await sendToTopFrame(tabId, { type: 'COLLECT', source: 'batch', naverPart: part });
```

`setRow` 비고 문구에 파트명을 넣어 어느 단계인지 보이게 한다 (예: `유입 렌더 검증 중`).

#### 3-4. `run(mode)` 루프 — 날짜별 2단계

```
index === 0 → chrome.tabs.create({url: urlFor(date), active:false})
index > 0  → chrome.tabs.update(workTabId, {url: urlFor(date)})
  ↓
collectPart(tabId, date, 'summary', index)
  성공 → statRows.push({store, date, ym, place_inflow, reservations})
  ↓
sleepWithStop(800 + Math.floor(Math.random()*701))   // 0.8~1.5초 파트 간 텀
  ↓
chrome.tabs.update(workTabId, {url: inflowUrlFor(date)})
  ↓
collectPart(tabId, date, 'inflow', index)
  성공 → channels/keywords를 롱포맷으로 펼쳐 inflowRows에 push
```

행 상태 판정:
- 둘 다 성공 → `success`, 비고 빈칸
- 하나만 성공 → `fail`, 비고에 `요약 OK / 유입 [CODE] 메시지` 형태로 **어느 파트가 깨졌는지 명시**
- 중단 → `stopped`

**파트별 독립 수집**: 요약이 실패해도 유입은 시도하고 그 반대도 마찬가지. 각 CSV는 자기 파트에서 성공한 행만 담는다.

`mode === 'range'`이고 다음 날짜가 있으면 기존 `randomRangeDelay()`(2~5초) 대기 — **현행 유지**.

#### 3-5. stale 렌더 가드 (필수 — 조용한 오염 방지)

가장 위험한 실패는 에러가 아니라 **틀린 값이 성공으로 저장되는 것**이다.
`chrome.tabs.update`로 URL만 바꿨을 때 SPA가 full reload 없이 라우팅만 하면
DOM에 이전 날짜 값이 남고, URL 검증도 안정화 검증(3회 연속 동일)도 **둘 다 통과**한다.

runner에 파트별 직전 시그니처를 들고 대조한다:
```js
// summary: `${place_inflow}|${reservations}`
// inflow : JSON.stringify({channels, keywords})
```

- 날짜 D의 시그니처가 **날짜 D-1의 같은 파트 시그니처와 완전히 동일**하면 stale 의심
  → `chrome.tabs.reload(workTabId)` 후 **해당 파트만 1회 재수집**
- 재수집 결과가 여전히 동일 → **진짜 같은 값**으로 판단하고 채택, 로그 `동일값 재확인`
- 재수집 결과가 다름 → stale 확정, 새 값 채택, 로그 `stale 감지`를 `'err'` 레벨로 기록
- 재확인은 **날짜당 파트당 최대 1회** (무한 루프 방지)

`mode === 'yesterday'`(1일)는 직전 날짜가 없어 가드가 동작하지 않는다 — 정상.

#### 3-6. CSV 출력 — 2개 파일

| 파일 | 헤더 | 조건 |
|---|---|---|
| `naver_stat_{매장}_{시작}_{종료}{suffix}.csv` | `store,date,ym,place_inflow,reservations` | **현행 그대로** |
| `naver_inflow_{매장}_{시작}_{종료}{suffix}.csv` | `store,date,ym,type,rank,name,ratio` | **신규** |

- `type` = `channel` \| `keyword`
- `ym` = `date.slice(0,7).replace('-','_')` (기존 규칙 동일)
- `suffix` = 해당 파트에서 실패/중단/누락이 하나라도 있으면 `_partial` (현행 규칙을 **각 파일에 독립 적용**)
- 성공 행이 0개인 파일은 만들지 않는다 (현행 동작)
- 기존 `toCSV()` / `downloadCsv()` 헬퍼 재사용. `background.js`는 `conflictAction:'uniquify'` 기본이라 별도 처리 불필요

출력 예시:
```
store,date,ym,type,rank,name,ratio
송파삼전점,2026-07-28,2026_07,channel,1,네이버지도,0.6054
송파삼전점,2026-07-28,2026_07,channel,2,네이버 플레이스광고,0.2575
송파삼전점,2026-07-28,2026_07,keyword,1,도리당,0.3000
```

#### 3-7. 작업 탭 정리

현행은 "전부 성공 + 다운로드 성공"일 때만 탭을 닫는다.
조건을 확장: **모든 날짜의 양쪽 파트 성공 + 생성 대상 CSV 모두 다운로드 성공**일 때만 닫고, 아니면 진단용으로 유지(현행 메시지 그대로).

  const deadline = Date.now() + timeout;
  let stableCount = 0, previousSignature = '', lastStateKey = '';
  let lastProbe = { success: false, errorCode: 'LOADING_TIMEOUT', error: '통계 화면이 준비되지 않았습니다.', diagnostics: {} };

  while (Date.now() < deadline) {
    if (this._stopFlag) return { success: false, errorCode: 'STOPPED', error: '수집이 중단되었습니다.' };
    const probe = this._probeReport(target);
    lastProbe = probe;
    const stateKey = JSON.stringify({ code: probe.errorCode || 'READY', /* ...diagnostics... */ });
    if (stateKey !== lastStateKey) {
      lastStateKey = stateKey;
      this._sendLiveLog(`${target} 준비 상태: ${probe.success ? '안정화 확인 중' : probe.error}`);
    }
    if (probe.success) {
      if (probe.signature === previousSignature) stableCount += 1;
      else { previousSignature = probe.signature; stableCount = 1; }
      if (stableCount >= 3) return { ...probe, stableCount };
    } else { stableCount = 0; previousSignature = ''; }
    await new Promise(resolve => setTimeout(resolve, 500));
  }
  if (lastProbe.success) return { success: false, errorCode: 'METRIC_UNSTABLE',
    error: `지표 값이 3회 연속 안정화되지 않았습니다. (확인 ${stableCount}/3, 20초 초과)`, diagnostics: lastProbe.diagnostics || {} };
  return { success: false, errorCode: lastProbe.errorCode || 'LOADING_TIMEOUT',
    error: `${lastProbe.error || '통계 화면 준비 실패'} (20초 초과)`, diagnostics: lastProbe.diagnostics || {} };
}
